# Agent 应用工程实战课

本仓库用于维护 Agent 应用工程课程的课纲、讲义和练习。

选一个可以判定成败的业务或工程问题，做成能独立演示、复现和解释的 Agent。每周都有一个设计问题、一段需要亲手实现的代码，以及一项可以判定成败的练习。第 4 周和第 8 周各有一个完整的交付点。

## 时间和学习目标

|周期|可用时间|完成时能展示什么 |
| --- | --- | --- |
|第 1–4 周|40–60 小时，上机 32–48 小时|一个 Java 命令行程序，一份与规则基线的对照结果，一条失败轨迹。 |
|第 5–8 周|再投入 40–60 小时，上机 32–48 小时|同一作品的检索、故障恢复与架构对照实验，以及一份能由别人复现的说明。 |

每周以 10 小时排必修，其中 8 小时上机、2 小时阅读和口述复盘。能投入 15 小时时，多出的 4 小时上机做选修实验，1 小时读扩展材料。可以在任一交付点收束。

## 实践选题

### 两个侧重信息检索的候选方向

| 课程项目 | 检索什么 | Agent 根据什么改变下一步 | 怎样验收 |
| --- | --- | --- | --- |
| 面向用户的 POI 语义搜索与智能简介 | 地点名称、类别、坐标、设施、服务说明，以及带来源和适用时间的场馆资料 | 明确地点名时直接检索。遇到自然语言需求时检索候选，再查看与需求相关的细节。信息冲突时核对分馆与开放区域，仍缺证据时标注未知或追问。 | 人工标注同一批查询，比较前 5 名相关性、明确约束违反数、简介中有证据支持的事实比例、耗时与工具调用数。 |
| 商户入网材料预审 | 带版本的课程规则、申请表和同一商户的附件片段 | 先识别业务类型和适用规则，再针对缺项或矛盾查证，生成补件清单或转人工的理由。确定性字段由程序核验。 | 用虚构规则和合成申请构造已知答案，评估错放、误拦、漏提的补件和条款引用。核对规则版本与申请时间。 |

**POI 搜索示例。** “周六 19 点，中关村某位置 3 公里内能带电脑学习的地方，最好有插座。”将半径、服务时段与设施偏好分别处理。用关键词匹配名称、别名，用向量召回与“自习、阅览”相关的服务文本。只在确有资料时写入插座、Wi-Fi 或预约要求。若时间信息只适用于少儿阅览区，应避免据此判断自习区当晚开放。每条简介聚焦“为什么符合这次需求、哪项还待确认”，并保留证据引用。[Elastic 混合检索](https://www.elastic.co/docs/solutions/search/hybrid-search) · [北京 12345 服务导图的分区时间示例](https://map.beijing.gov.cn/place?categoryId=tsg&placeId=66b066ffe4a9ed67df2d567e)

**商户预审示例。** 课程虚构规则允许连锁门店通过关系证明解释申请主体和门店名称差异。收到名称不一致的申请后，程序标记差异，Agent 查找适用条款和附件。有对应证明时，返回证据并继续核验；缺少证明时，列明需要补交的材料。可设计两份仅相差一份附件的样例，检查结论是否随证据改变。这套规则适用于课程沙箱。

**建议的四周规模。** POI 方向先选一个区域、一类需求（如自习与阅读），收集 30–50 个地点并核实部分地点的详细资料，准备约 20 条人工标注查询并留出新题。依次实现关键词基线、固定混合检索加简介、允许按需查证的 Agent，分别衡量语义召回和追加查证的收益。审核方向先限一种业务、两三个材料类型及少量虚构条款，先做程序核验基线，再加入材料检索和解释。两个方向均为选题建议。

### 其他练习方向

前四周可以选择以下任一方向。现有逐周课纲以 POI 为示例。换题时，保留执行循环、证据获取、基线和留出评测，将工具、输入数据和判分规则改为对应场景。以下均为课程设计示例。

| 候选项目 | 用户任务与 Agent 决策 | 四周可做的范围与验收 |
| --- | --- | --- |
| 订单售后办理 | 用户想换货，需要识别是哪笔订单，查询库存，缺货时询问用户是否接受替代方案。 | 用本地 JSON 或 SQLite 模拟订单、库存和售后单。检查办的是哪件商品、是否得到用户同意、是否只生成一张单。 |
| 支付运营数据分析 | 商户问本月手续费为什么上涨。Agent 查费率口径、选分组维度，并根据中间结果决定是否下钻。 | 用合成交易表和两份费率说明，构造交易量、交易结构或费率变化的对照题。用独立 SQL 验算金额和分组贡献，信息不足时检查是否注明缺口。 |
| Java 缺陷复现 | 输入一条 Issue，Agent 找代码入口、运行针对性测试，根据报错缩小范围，产出最小复现。 | 取一个可本地构建的 Maven 仓库和已知缺陷。用同一条复现测试在缺陷版本跑红、修复版本跑绿，核对失败原因，防止把构建环境问题算成复现成功。 |
| 微服务故障排查 | 接口延迟升高后，Agent 决定先查哪个指标，再根据结果读调用链、查配置差异或补取日志。 | 固定两三个服务，回放预制的连接池等待、下游超时等故障。核对故障注入记录、定位证据和排除理由，保留一条证据不足的题。 |
| 技术调研与选型 | 用户要给 Java 项目选 MCP 实现。Agent 拆出版本兼容、传输方式等问题，检索官方文档，对冲突说法追加核验。 | 限定两个候选实现并固定资料版本。逐项核对引用是否支持说法，对一项可运行的能力用小实验验真。 |

**从哪里开始。** 想完整练习多轮交互、工具调用和有副作用的写操作，可以选订单售后。想展示数据分析与业务判断，可以选支付运营。偏好开发者工具，可以选 Java 缺陷复现。做故障排查时，第一版可以先回放采集好的数据，把时间留给诊断逻辑。

公开资料可借用任务设计和评测方法，课程里的具体案例可自行构造。

- 支付数据分析参考 Adyen 与 Hugging Face 的 [DABstep](https://huggingface.co/blog/dabstep)，其公开任务涉及手续费和欺诈分析。
- 缺陷复现借鉴 [SWE-bench](https://github.com/SWE-bench/SWE-bench) 的可执行验证。该基准的正式任务要求提交修复补丁，课程第一版只要求复现。
- 故障注入与遥测参考微软的 [AIOpsLab](https://github.com/microsoft/AIOpsLab)。
- 调研报告与引文质量评测参考 [DeepResearch Bench](https://deepresearch-bench.github.io/)。

## 贯穿题目（POI 示例）

给定查询、目标 POI ID 和一份搜索调试日志，回答“目标最后出现在哪个已记录环节？能从哪条记录判断原因？”程序按字符串查 ID、校验字段、标记阶段覆盖情况。模型根据当前证据决定继续查哪项材料，或给出带引用的结论。

演示数据均可自造。假设目标 P007 在排序输入出现，在最终列表消失。若过滤记录中包含该 ID 和原因，报告可引用原文说明原因。若过滤记录缺失，正确答案应保留“最后见于排序输入”，并明确还缺哪项证据才能归因。

## 技术选择

建议用 Java、Maven、JUnit 和一个支持工具调用的模型接口完成核心课。用命令行读取本地 JSON，保留模型和工具的可替换接口。Python 用来阅读 LangGraph 源码，Rust 用来跟读 Codex 的一条调用路径。先复用熟悉的工具，把上机时间留给 Agent 自身的行为。

第一周先用自己的可用接口，或支持工具调用的本地模型，跑通“一问一工具一回传”。暂时缺少模型时，照常上课，用脚本化响应测试循环、错误处理和回放。第 4 周可交工程版；保留“真实模型选工具”和“留出题效果对照”两项待补，实测后再完成核心课验收。

## 核心课

第 1–4 周　把一个案例做到可回放，再验证方法能否迁移到新题

### 第 1 周　从一条日志建立基线

**原理**　用固定流程回答能精确判断的问题。理解消息、工具描述、工具调用 ID 和工具返回值各自在一次模型交互中的作用。读 Hello-Agents 第 3 章选段及第 4 章 ReAct 小节。

**上机 8 小时**　用 2 小时手写 4 个案例及答案，3 小时实现 Java 基线，2 小时调通模型与一个只读工具，1 小时回看一次真实的请求与返回。案例覆盖最终命中、明确过滤、阶段缺失和工具读取失败。

**验收**　从命令行运行同一个案例，展示程序如何找到证据，再指出真实工具调用中“模型请求”和“本地执行”的边界。工具读取失败应作为执行错误单列。

### 第 2 周　手写一次完整的执行循环

**原理**　模型每次返回最终答案或工具调用请求。程序负责校验、执行、回传结果和决定是否允许下一轮。读 ReAct 论文摘要和一个交互示例，理解新观察如何改变下一步。

**上机**　实现“查目标位置”和“读指定阶段”两个只读工具，记录调用 ID、参数、结果和终止原因。设最大轮数。准备脚本化响应，重现未知工具、非法参数和重复调用，再用真实模型跑一例。

**验收**　一次运行能连续查两个工具再回答。另一条运行在达到轮数上限时终止。能从轨迹指出最后一个有用的观察。选修：构造同一轮两次工具调用，验证结果与调用 ID 正确匹配。

### 第 3 周　用有限上下文找到足够证据

**原理**　比较整段日志、截断片段和按需查询。关注证据覆盖、结果长度及引用是否能回到原文。读 Hello-Agents 第 9 章。

**上机**　用合成记录扩充到约 3 MB，保留原始输入和稳定的记录位置。工具先返回阶段摘要，模型需要时再取明细。将开发案例扩到 8 条，另备 4 条留出题，封存答案，在第 4 周之前不用于调试。

**验收**　把关键证据放在日志尾部，比较固定长度截取和按需读取的结论、输入 token 数与引用。区分“整个列表都查过”“仅查过前几条”和“该阶段缺失”。

### 第 4 周　在新案例上完成首次评测

**原理**　人工先写判分标准，代码核对字段和引用；人工复核结论是否超出证据。读 Hello-Agents 第 12 章和 Anthropic 的 Agent 评测实践。

**上机与验收**　用同一组 4 条留出题比较规则基线与单 Agent，按下文评测口径留存逐题结果。先在开发集复现一处失败，修改一个因素并回归，再冻结方案做留出评测。演示一个成功案例和一个失败案例，5 分钟内讲清选择、证据和局限。只有一个月时在这里结课。

## 进阶课

第 5–8 周　用同一批任务决定检索、恢复和任务拆分是否值得做

### 第 5 周　让 Agent 查到规则说明

**原理**　检索增强生成（RAG）让模型引用外部资料。记录事实与解释规则来自不同数据源，分别测才能知道是没检索到，还是拿到资料后解读错误。读 Hello-Agents 第 8 章。

**上机与验收**　写 6 则简短规则说明和 4 道带同义表达的新题，为每题标注需要的文档。实现一个按词检索工具，对比开启前后的规则引用和答案。列出前 3 个结果包含目标文档的题数、最终答对的题数，并解释一个差异。选修：比较 BM25 与向量检索。

### 第 6 周　处理超时和中断

**原理**　区分只读操作与有副作用的操作，区分模型重试与工具重试。学习会话状态、执行步骤、重试预算和检查点之间的关系。

**上机与验收**　为一步工具调用注入超时，再在结果持久化后、回传给模型前模拟中断。用本地文件记录步骤和调用 ID，重启后复用已完成结果。展示一次有上限的重试、一次恢复，以及中断前后的执行记录。选修：将原有只读工具经 MCP 的 tools/list、tools/call 暴露给另一个客户端。

### 第 7 周　比较固定流程与动态规划

**原理**　固定流程由代码安排顺序，单 Agent 根据观察选动作。先计划再执行需要处理计划失效，子 Agent 协作则要处理上下文交接与部分失败。

**上机与验收**　在同一组 4 道开发题上比较第 1 周固定流程、第 2 周循环，再为其中 1 道需查两种证据的题实现“两步计划，可重排一次”。记录正确题数、调用数、耗时及失败点，给出保留哪个方案的理由。选修：把两种证据交给两个只读 worker，测增益与额外开销。

### 第 8 周　复现结果并准备技术面试

**上机与验收**　补充 4 条未参与调试的新题，冻结版本后复测。保留运行命令、模型版本或标识、样例输入、逐题结果、两条执行轨迹和一页设计取舍。找同伴或在干净目录按说明复跑，记录复现差异。用 8 分钟演示，再用 5 分钟回答一次失败和一种未采用的方案。

### 源码阅读怎么做

第 2 周先在 Spring AI 看 executeToolCalls 怎样把工具结果拼回消息。第 6 周读 LangGraph 的 ToolNode，追一次工具异常如何返回，对照自己的错误处理。第 7 周沿 Codex 的 spawn 与 wait 追一次子任务派发和等待，标出“派发成功”与“任务执行完成”分别在哪里表达。每次约 45 分钟，计入该周阅读时间。源码链接见文末。

## 评测与求职作品

能让面试官复核的结果，比抽象地描述“做过 Agent”更具体

### 用同一把尺子比较实现

|记录项|怎样判 |
| --- | --- |
|答对了几题|事先标注最后可见阶段、可支持的结论和允许引用的记录。对可诊断题，三者均正确才算通过。对证据不足题，准确说明已知事实和缺失证据也算通过。 |
|有没有编造原因|报告给出原因时，逐一检查引用是否存在、是否支持因果判断。单独列出无依据归因的题数，以防总分掩盖严重错误。 |
|花了多少代价|同输入、同模型标识和同预算比较两种模型方案，记录调用数、耗时、输入与输出 token。若接口返回用量且有对应单价，再换算金额。纯规则方案的模型调用数为 0。 |
|结果是否稳定|每条留出题至少各跑一遍。挑一个可能波动的模型案例再跑两次，保留三次结果。技术故障单列并计入未完成。证据不足但回答正确可判通过。 |

4 条留出题的结果写成“几题 / 4”，附案例类型和失败样本。看过答案后，可把它们纳入回归集。后续声称对新题的效果时要另备样本。若规则方案更好，说明它在哪些条件下已足够。

### 把项目讲成一次工程决策

建议用五个问题组织面试演示：用户原先怎样排查？什么证据能支持结论？为什么把这一步交给模型？哪次失败改变了设计？在新题上得到了什么结果？简历填写实测题数、通过数和条件。个人实验的运行结果按个人项目表述。
