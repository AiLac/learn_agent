# Agent 应用工程实战课：自习室语义检索与智能简介

用 Java 构建一个能够根据自然语言查找香港自习室、核实开放条件并生成地点简介的搜索 Agent。每周沿用同一套公开数据和同一个程序入口，逐步回答一个工程问题：一次检索能解决哪些请求，哪些请求值得让模型继续查证？

## 怎样用这套讲义上课

初次学习从[第 1 天的教师示范与可运行例题](lessons/week-01/daily.md)进入。以后每次打开当天编号，沿下面三步学习。

1. **先看一遍老师怎样求解。** 阅读当天的概念和走例，先预测工具或代码的返回，再对照讲解。如果不明白“为什么这样设计”，读本周理论页开头的精讲；源码阅读按文中指定的类或方法进入。
2. **关掉参考解，自己改一个条件。** 每天有独立题和折叠的参考解。先在纸上或测试里写下预期与理由，动手执行，再展开答案。结果不一致时，定位最早偏离预期的一步。
3. **用一道新题验收。** 按“过关”要求换一个输入，说明输入变了什么、预期哪一步跟着变、程序实际怎样。如果只能复述例题，回到本周实践页的带解示范，再做一遍同类变式。

第一天的实验从真实名录读取 36 条记录；Python 标准库负责送入数据，Java 负责匹配、计数及截断。JDK 17+、Python 3.9+，不需要模型密钥。更新或克隆仓库后，从仓库根目录运行：

```powershell
py -3 examples/day-01/run.py "油尖旺" --limit 1
```

预期第一行是 `status=OK scanned=36 totalMatched=2 returned=1`。先解释为何屏幕只有一行而命中了两条，再改 `--limit 2` 验证。加入 `--simulate-timeout` 可观察“执行失败”与“成功但没有命中”的区别。Linux/macOS 使用 `python3` 启动。

## 不同阶段用哪份数据

第 1 周沿用可手算的 36 条入门样本。第 2 周起的检索、取证和简介实验切到[扩展数据集](data/hk-study-rooms/search-v2/README.md)：194 个地点均有简繁中英文名称与坐标，79 张来源证据覆盖其中 40 个地点。配有 12 道开发题，包括充电、预约、季节限制、直线距离和资料范围混淆。将这 12 题与自己冻结的留出题分开；生产规模压测还需要另外的索引规模与负载证据。

## 每周讲义

每周先用约 2 小时读理论、走读案例与源码，再用约 8 小时完成上机练习。建议把同一份 Java 项目逐周扩展，记录实际运行结果。前 8 周完成一个可演示的应用；第 9–10 周为新增的架构设计与性能优化专题，按每周 10–15 小时另需 20–30 小时。若目前只能投入两个月，可先完成第 8 周，在后续两周继续生产专题。

**从第 1 天开始。** [第一课：一次搜索命中，到底回答了什么？](lessons/week-01/daily.md)。10 周共 70 个学习日。每日页按“讲解 → 课堂推演 → 动手 → 过关”组织；理论与实践讲义供当天深入阅读。每周第 1 天 90 分钟，第 2–5 天各 75 分钟，第 6 天 150 分钟，第 7 天 60 分钟，合计 10 小时（阅读与讲解 2 小时，上机 8 小时）。额外时间用于选修或重做未掌握的实验，学习日可按个人日程顺延。

## 课程目标与时间

- **第 1–4 周，40–60 小时。** 从一条真实查询出发，交付可运行的单 Agent、语义检索、带出处的简介和首次对照评测。只投入一个月时可以在这里结课。
- **第 5–8 周，再投入 40–60 小时。** 加入多轮追问、工具故障恢复和规划实验，形成可复现的求职作品。一周按 8 小时上机、2 小时阅读与口述安排必修；有余力时增加 4 小时实验、1 小时阅读。
- **第 9–10 周，生产专题。** 选出一种时延敏感的部署方案，用同负载实测优化前后差异，并报告正确性、超时、成本与回滚条件。
- **建议技术栈。** Java、Maven、JUnit、一个支持工具调用的模型和一个中文可用的文本向量模型。194 条课程地点记录可以在内存里算余弦相似度、融合两路排名。已有 Elasticsearch 环境时可用它实现同一对照。脚本化模型响应用于测试程序分支，选工具和生成简介的效果用真实模型评测。

## 项目输入与输出

输入示例：“按 11 月常规时间，周六晚上七点在旺角花园街能找个地方温书吗？” 输出包括地点名称、针对需求的简短说明、适用时间和事实出处。证据不足时指出哪一项仍未知。用户追问“改成周日呢？”时，系统应沿用地点、月份和时刻，只更新星期。

## 核心课

### 第 1 周　模型、工具与任务边界

**要弄懂的问题**　用户输入一句话后，模型可提出什么请求？哪段程序真正读了数据？先理解消息、工具描述、调用 ID、工具结果与最终回复。

**上机**　读入 36 条 JSON；用名称、地区、地址做关键词检索，按编号去重。写一个只读工具 `search_rooms`，跑通模型请求工具、Java 执行、结果回传、模型回答的最小交互。先写 4 道开发题，覆盖名称直查、地区查找、时段问题和资料缺失。开始做第 2 周的检索调参前，另按问题组封存 8 道留出查询及证据答案；同一地点同一意图的星期改写归同组。第 2、3 周各补 4 道开发题。

**验收**　能展示一次真实的请求与工具结果；能指出哪道题用名录就够了、哪道题必须查时间表。首次上机可以先花 90 分钟：20 分钟读样本，40 分钟做两个关键词查询，30 分钟手工写出花园街的周末对照答案和出处。读 Hello-Agents 第 1、3 章选段。

### 第 2 周　语义召回与检索增强生成

**要弄懂的问题**　名称直查、语义相似和事实约束各解决什么？理解 embedding（文本向量）、关键词与向量结果融合，以及 RAG 怎样用取回的证据生成答案。

**上机**　给花园街等 3 个分馆整理有出处的证据卡，每条注明场馆编号、适用服务区域、事实和来源。对比关键词检索（含简单同义词）与关键词加向量的混合检索；记录同一查询两路各召回了什么。先做固定流程，按查询中的地点、时段或设施提取条件，检索一次，给前两名各取一次相关主题证据，再生成带出处的两句简介。两个检索器使用相同的 194 个候选和文本字段（名称、地址、地区、已采集的带来源描述）。缺少资料的地点保留在候选池。8 小时可按采证 2 小时、检索实现 3 小时、固定流程 2 小时、核对 1 小时分配；批量采集更多分馆作为选修。

**验收**　选名称直查、口语表达“温书”、含时间条件三种题并排看结果。这些地点都提供自修用途，单靠“温书”无法区分各馆；要检查地区、名称及服务证据有没有把合适候选排在前面。按自己标注的相关性记录得失，允许关键词基线胜出。读 Hello-Agents 第 8 章与 Elastic 的混合检索说明。

### 第 3 周　手写单 Agent 执行循环

**要弄懂的问题**　程序预先规定的检索顺序，和模型根据工具返回值决定下一步，行为上有什么区别？读 ReAct 的行动与观察循环，对照原生工具调用实现。

**上机**　沿用上周的检索器、模型与同一套证据，增加 `lookup_evidence(room_id, topic)`。手写循环处理工具名、参数校验、调用 ID 匹配、结果回传和停止条件。允许模型直接回答、继续查证或追问。保存工具轨迹、耗时和终止原因。限制轮数并用测试重现未知工具和重复调用。为便于第 4 周公平对照，两种方案均使用同一工具与证据库，每题最多 3 次工具调用、相同的单次返回条数和相同的简介要求。Agent 可在此预算内重搜或追加查证，实际使用次数单独计量。

**验收**　现场跑三题：查地址时使用名录即可；查周六 19:00 是否开放时能追加时间证据；只给名录和时间表、再问实时余座时能如实说明未知。逐条核对简介里的事实与引用。读 Hello-Agents 第 4、7 章选段和 Spring AI 工具执行源码。

### 第 4 周　评测与失败诊断

**要弄懂的问题**　一次答对可能来自更好的召回、更完整的证据，也可能只是这次模型选对了工具。怎样分别检验这些解释？

**上机**　使用前三周积累的 12 道开发题和调参前已封存的 8 道留出题。先在开发题调整，再一次性运行留出题，保留全部结果。冻结数据、程序和模型标识后做两组对照：只改变召回方式，比较排名；固定混合检索器、证据库与生成模型，比较固定流程和按需查证 Agent。

**验收**　按下表记录逐题结果，复盘一个失败。区分地点未召回、证据未找到、适用条件判断错误、简介写出无依据事实。交付可运行入口、评测表、成功与失败各一条轨迹。读 Hello-Agents 第 12 章和 Anthropic 的 Agent 评测实践。

## 进阶课

### 第 5 周　多轮对话、上下文和状态

**上机**　处理“换成周日呢？”、“那油麻地呢？”、“附近还有别家吗？”。为当前地点、时间、硬条件和偏好建立会话状态，写清哪些字段保留、更新或失效。仅将当前问题需要的证据送给模型。缺少位置时先澄清或按用户给出的地区查找。

**验收**　同一段对话中，换星期后开放判断改变；换分馆后引用也改变；重复运行不会把上一个用户的地点带入新会话。读 Hello-Agents 第 9 章，画出一次状态更新前后差异。

### 第 6 周　工具协议与故障恢复

**上机**　使用一个现成 MCP SDK，把已有证据查询暴露为只读工具，理解工具发现和调用分别传递什么。用本地缓存的公开证据制造“查到空结果”和“工具超时”两个不同情形，定义可重试错误和重试上限。源码对照 Spring AI 与 LangGraph 怎样处理工具结果和异常。

**验收**　程序能区分“资料没写开放时间”和“本次查询失败”，超时达到上限后给出可解释的降级答复。选修：工具结果落盘后中断进程，恢复时复用这次结果。读 Hello-Agents 第 10 章和 MCP 工具协议。

### 第 7 周　规划与子 Agent 的适用条件

**上机**　给出一道需要比较两馆的问题，例如“按 11 月普通周六时刻表，花园街和薄扶林哪间 19:00 还可自修？”将单 Agent 逐次查证与“先列两项核验任务，再执行汇总”的流程放到同一题上。故意让一路工具超时，检查汇总时如何处理部分结果。

**验收**　列出两种做法的正确性、耗时、调用数及失败时的表现。沿 Codex 的 spawn 和 wait 读一次子任务派发与结果返回，画出“已派发”和“已完成”的区别。选修：真正派发两个只读子 Agent，与并行执行两个普通工具作对照；后续是否保留，由实测决定。

### 第 8 周　复现与面试作品

**上机**　新增至少 4 道未参与调试的查询，在冻结版本上复测；记录数据快照、模型标识、运行命令、已知限制与复现步骤。从干净目录执行一次。准备 8 分钟演示：名称直查、复杂时间条件、多轮改问、一次失败，以及你基于证据做的改动。

**验收**　别人能够复跑同一查询并找到对应的资料与工具轨迹。能回答“向量召回带来了什么”“什么时候一次固定检索就够了”“追加查证值不值得额外延迟”。面试材料用实际样本数和结果描述本项目。

## 第三阶段　面向时延敏感场景的架构设计与优化

### 第 9 周　架构设计与比较

以字段直查、时段核验、多馆比较、歧义或证据不足四类查询作对照。先保持工具集、数据、模型、正确性口径和工具上限一致，比较固定工作流、ReAct 与 Plan-and-Execute，再实现可回退的请求路由。并行工具与独立子 Agent 分开记录，绘制一次请求的关键路径。验收产物是逐查询桶的路由决策表，以及一次误路由或部分失败的处理证据。

### 第 10 周　性能压测与优化

将时延目标落实到客户端收到第一条可用事实、正确完成请求和终态尾延迟。先做冒烟验证，再逐档改变到达率，分开记录冷/热缓存和真实/回放模型。以固定负载和质量判分复测一次单变量优化，给出成本、超时、质量回退与回滚依据。[可运行的压测探针](bench/load_probe.py) · [公开数据冒烟题](bench/smoke-cases.json)

## 怎么判成绩

| 维度 | 记录方法 |
| --- | --- |
| 搜得对 | 单一目标题记录是否进入前 5；多候选排序题独立按地点、地区和服务意图标注相关性（0/1/2），再比较 nDCG@5，并查看具体升降的地点。时间与设施是否有证据满足，放到下一项单评。缺少证据卡不等于场馆关闭。无匹配题单列。 |
| 答得对 | 核对地点、地区、目标时段和服务区域。明确约束有一项违反，该题记为失败。证据确实不足时，准确指出未知项可以通过。 |
| 简介可信 | 将简介拆成可验证的事实，逐条核对引用、适用范围和日期。同时统计应回答却被标成“未知”的项目，避免靠省略内容获得高分。 |
| 运行代价 | 同题记录模型调用数、工具调用数、耗时和 token。对易波动的一题重复运行 3 次并保留各次轨迹。少量留出题报告通过题数和分母。 |
