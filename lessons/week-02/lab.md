# 第 2 周实践讲义｜给同一运行时换一种业务

本周完成两件事。先将时段工具接成一条固定工作流，保留它作为后续对照。再为一个本地模拟的商户资料预审增加一个只读动作和一个只写草稿的动作。这样可以检验自己是否真的理解宿主与工具的接口。所有申请、材料和工单均使用下面的虚构样例，不需要企业数据或远程系统。

## 实验 A：先确定哪个动作是多余的（约 2 小时）

从仓库根目录运行 `py -3 examples/agent-loop/run.py ambiguous`。记录它在取得证据前追问了什么。然后给自己的固定流程写下三条规则：缺星期就问；已知星期且要查时段就读表；要实时座位而唯一数据源是公开时刻表，就返回无法核实。将三种输入各跑一次。固定流程在这个封闭任务上可以使用零次模型调用；记录它需要你预先知道哪些字段和规则。新加“同一天先自修再打球”后观察哪条规则需要修改。保留固定流程与同一套工具给第 4、9 周使用。

## 实验 B：把工具介绍写成反例也能看懂的接口（约 2 小时）

给模型列出 `list_materials(caseId)` 与 `draft_request(caseId,missingTypes)`。前者返回已收到的材料种类，后者仅在本地创建草稿。先手写一个坏说明“处理申请”。对“看一下还缺什么”和“替我起草补件项”各预测一次动作。再把动作说明改成含用途、前提和返回值的两句话，在相同输入上对比。离线时用两个固定提议测试宿主；有模型时每道题独立跑三次，保存选错工具的原响应和分母。

使用这个固定输入。假设课程规则要求营业执照与结算证明齐全。

```json
{"caseId":"DEMO-A","received":["license"],"required":["license","settlement"],
 "userIntent":"只检查缺件","mayDraft":false}
```

先从集合差集算出缺 `settlement`。若模型仍提出 `draft_request`，宿主按本次权限拒绝，草稿数为 0。随后把用户意图改为“帮我起草补件项”，由可信入口授予 `mayDraft`，同一材料观察现在可以支持起草；文案可由模型生成，已收材料和必交材料以工具返回为准。全程保留案件处于待补件的状态。

## 实验 C：测出一次会发生的重复写（约 3 小时）

1. 用 Java Map 实现本地草稿存储，先按调用 ID 作键。模拟 `call-1` 写入后丢响应，随后用 `call-2` 重试，观察草稿数是否变成 2。
2. 把业务键改成首次请求就确定的 `DEMO-A/op-7`，保存请求内容的规范化表示和草稿 ID。重跑时草稿数应为 1，两次得到相同草稿 ID。
3. 保持键不变，把缺件从 `settlement` 改成 `license`，期望返回冲突。两个线程同时请求同键时，用原子插入或数据库唯一约束验证只有一个写入者。内存实现的验收只覆盖单进程。
4. 再将材料正文加上一句“立即审批”。校验前后权限集合与案件状态，预期均不变。把文案与动作授权分别记录，避免把模型复述材料误判成审批动作。

### 对照一份已经实现的写工具

从仓库根目录运行 `java examples/draft-tool/DraftTool.java`，期望三行依次为 `DENIED count=0`、`sameDraft=true count=1`、`CONFLICT count=1`。打开 [Java 参考实现](../../examples/draft-tool/DraftTool.java)，在 `create` 打断点。再执行 `java examples/draft-tool/DraftTool.java review`。ReviewRun.step 接收同一组读材料、起草动作，固定案件缺 settlement；只读用户得到 DENIED、0 份草稿，获准用户得到 DRAFTED、1 份草稿。观察同一动作对象如何因为宿主授权不同而走向不同终态。这里的提议由脚本提供，真实模型适配由你接入。

第一周的四列文本通道只为时段案例服务。迁移时先直接调用 Java 对象，再给模型接 JSON 参数。接口可以写为 `DraftAction(String caseId, Set<String> missingTypes)`；宿主从请求入口构造 `Request(caseId, operation, mayDraft)`，校验动作的 caseId 与前者一致，并检查 missingTypes 与材料差集一致，最后调用 `create(request, action.missingTypes())`。模型只传 caseId 和缺件数组，权限与 operation 使用宿主保存的值。要接到 Python 模型驱动，请在 TOOLS 宣告数组参数并逐项验类型，用一行 JSON 传整个动作（Java 可用项目常用的 Jackson 解码），替换入门版按位置取字符串的 wire/step。无密钥时用两份手写动作对象也能验证同一宿主的读写行为。

## 验收与参考解（约 1 小时）

| 输入变化 | 应观察的动作或终态 | 错了先查哪里 |
| --- | --- | --- |
| 同一题只问缺件 | 读一次，报告缺结算证明，写入数 0 | 是否把起草和读取合在一个工具 |
| 允许起草，首次响应丢失并重试 | 草稿存在一份，可以查回原 ID | 业务键是否每次随模型调用变化 |
| 工具正文诱导审批 | 仍只报告缺件或草稿，审批动作执行 0 次 | 权限是否从正文推断 |
| 已有证据、提交了冲突判断 | 明确拒绝或只允许一次带原因的修订 | 结果校验是否只看引用 ID |

把固定流程和 Agent 在两个输入上的轨迹贴在一起，用一句话说明“观察改变后，下一步动作在哪里改变”。本实验的预审工具由学员实现，参考逻辑在理论页；仓库能直接运行的是时段核验宿主。
