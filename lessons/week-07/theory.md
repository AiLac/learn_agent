# 第 7 章　规划、并行和多 Agent：把一句目标变成可以执行的工作

“帮我判断两家场馆哪家能去，有资料冲突时再核实。”如果地点 ID、日期和证据来源都已给出，你可以用两个 Java Future 并行读表。如果每个场馆都有多个服务区域，资料互相矛盾，还需要在有限时间内自行换来源，那么两个分支内部都有新的决策。两道题看似只差一句描述，架构成本却截然不同。分析先从任务依赖开始。

## 先规划究竟预先决定了什么

计划应至少表示子目标、输入、依赖和可验收的产出。写“研究 A、研究 B、写报告”，对人是合理提纲，对程序却缺少判断完成的条件。用业务命题代替模糊描述：“检查 A 在指定时刻是否满足条件，返回 FOUND、NO_DATA 或 ERROR 及支持的证据。”这样，即使 B 失败，执行器仍能知道 A 已完成到哪一步。Plan-and-Solve 强调分解与求解；工程上的 Plan-and-Execute 还要处理计划校验、调度与中间结果失效。原论文中的提示方法并不等同于可持久化的生产执行器。[Plan-and-Solve 原论文](https://arxiv.org/abs/2305.04091)

给定 A=查甲馆，B=查乙馆，C=比较。依赖是 A→C、B→C，A 和 B 可以在同一资源上限允许时并发。若再加 D=当 B 缺资料时查备用来源，D 依赖 B 的观察，是条件分支；C 要等待 B 的可靠结论或 D 的终态。一次生成的静态计划能包含这个条件，前提是设计时已经知道它。对未预期的证据冲突，可以向规划器提供已完成事实和剩余预算，请它重写未完成部分。不要让新计划无条件抹掉既有观察，尤其不要再次执行已经产生副作用的动作。

## 执行器如何证明一张计划图可以运行

在派发前检查节点 ID 唯一、依赖节点存在、工具在授权集合内、图没有环。对无环性，可以从入度为零的节点开始：取出节点，删除它到后继的边，任何入度降为零的后继都可以排入队列；如果处理完的节点数小于总数，剩余部分含未消解的循环依赖。这里要区分两种队列：拓扑检查用的是计划描述，执行队列的入度更新则需要等待真实前置任务达到规定状态。拓扑验证通过，只证明依赖结构可能执行，并不保证工具运行成功。

以 A、B、C 为例，最初入度 (0,0,2)。B 先完成，C 降到 1，不能开始完整汇总；A 到达终态后，C 才可决定完整回答还是部分回答。若 A 超时也算“已到终态”，意味着 C 可以运行，但不能把“超时”填成“不符合”。执行条件与业务成功条件分别表达，才不会因为代码里 `CompletableFuture.allOf` 已结束，就向用户声称所有事实都已证实。对会异常完成的 Future，还需把异常转换成明确的分支结果或独立收集，避免一个异常遮掉其他已成功的事实。

“11 月普通周六 19:00，花园街和薄扶林哪家还能温书？”同一个比较维度，两个独立的证据对象。花园街到 20:00，薄扶林普通周六到 17:00，因此常规安排下只有花园街符合。如果薄扶林查询超时，你只能确认花园街符合，不能继续声称“只有”一家符合。[官方时刻表](https://www.hkpl.gov.hk/tc/locations/opening-hours-04.html)

## 并行怎样省时间，多 Agent 又怎样增加成本

当 A、B 是两个已知参数的查询，用两个普通工具就能并行，不必生成两份系统提示、两段对话和两次模型调度。子 Agent 多提供的是**分支内独立决策**：给目标与资源上限，它能在碰到异常后自己选择下一动作。由此也多出三项责任：父任务有无把完成条件说清；子任务有无获取完成目标所需的证据与权限；父任务如何核对返回结果。两个模型一起给出相同说法，也可能只是依赖同一个错误来源，不能算独立证实。

在请求图上标注资源才看得见真正的并行度。设父规划 400 ms，两次读取分别 100、180 ms，归并 40 ms，最终生成 350 ms。无排队时并发关键路径为 970 ms；若两个 worker 各要串行做一次 500 ms 模型决策，且共享并发上限为 1，后启动的分支至少要等前一个释放模型槽。团队规模增加了，吞吐却可能下降。反过来，分支内需要独立探索时，隔离上下文可以降低不相关证据互相干扰的机会。两种效应方向相反，必须用同样任务与模型限额比较。

## 父任务怎样区分“派出”“结束”和“业务完成”

在课程固定版本的 Codex 中，派发工具为子任务建立执行并返回可寻址的目标；等待路径订阅状态并有截止时间。持有子任务标识只证明能定位它。等待者本轮超时并不能推出子任务已停止，worker 报“完成”也不能包办父任务的业务验收。父任务应记录 runId、taskId、计划版本、状态和来源，将返回的事实关联回原子目标。链接中的固定版本用于核查这两个职责分开的源码位置。[Codex 派发](https://github.com/openai/codex/blob/748ab55ca7de0b647d9a7a9d9a8e70e00f28666d/codex-rs/core/src/tools/handlers/multi_agents/spawn.rs) · [Codex 等待](https://github.com/openai/codex/blob/748ab55ca7de0b647d9a7a9d9a8e70e00f28666d/codex-rs/core/src/tools/handlers/multi_agents/wait.rs)

考虑重规划竞态。版本 1 的任务 B 仍在运行，版本 2 已用新日期启动 B′。B 的迟到回执虽然包含正确的旧日期事实，却不能覆盖版本 2 的当前结论。以复合标识关联到原任务，把过期回执保留为审计事件，必要时可复用仍适用的只读事实。取消也可能与完成同时发生，设计需指定“对用户已经发布的终态能否修改、由谁修改”。这些问题用普通并发工具就可能遇到，多 Agent 还多了模型自报完成与上下文隔离。

## 把计划迁移到 POI 故障定位

给诊断 Agent 的目标是“确定预期地点 P 第一次在哪个可观察环节没有出现”。一个 worker 看召回阶段，一个看排序阶段，第三个写总结，看起来很工整。但排序 worker 需要的输入是否存在，取决于该请求有没有记录排序输入。如果把每个 worker 的任务写成“找出排序丢失的原因”，它很容易接受一个尚未证实的前提。更好的任务是“在这份公开教学轨迹的排序输入和输出中分别报告 P 是否可见、记录范围和证据位置”。父任务收到“未记录”，便知道不能继续声称“排序过滤”。

同一轨迹上，若只是按 ID 判断集合成员关系，这项工作可以交给 Java 解析器进行完整扫描；模型只在多份结果之间解释证据冲突或选择追加观察时参与。若日志内容很大，worker 可获得按任务裁剪的证据和回查句柄，不必复制整份日志。这样设计既复用了检索调试经验，又把学习焦点放在委托契约、证据边界和停止政策。例子是模拟接口，不需要使用任何内部日志。

## 调度器里最难的一个字：“等”

Java 工程中常写“等两个分支完成再聚合”。在 Agent 系统里，至少要定义三种不同的等待政策。第一种是全部终态：每个必需分支都成功或明确失败后再给完整比较。第二种是首个可用结果：只要某项满足用户条件就可以结束并尝试取消其余分支。第三种是到截止时间收集已知部分：允许提前发布单项事实，但不能用“只有、最好、全部”这类量词覆盖缺失分支。选择哪种政策由任务的语义决定，不能为了性能直接从第一种换成第二种。

对“哪家符合”这一含混问法，把义务说清尤其重要。若用户要一个可行选项，找到甲就可终止；若用户要列出两家中所有可行项，乙未返回时只能给部分结果。可以把合并器写成下面这个判定。它是教学伪代码，读法是先决定证据充分性，再决定措辞。

```text
如果目标为“找任一可行项”且已有证实的可行对象：返回该对象与引用
否则，如果全部必需对象都有适用证据：逐项比较并说明完整结果
否则，如果尚有时间且还有能补足缺项的动作：继续等待或补查
否则：返回已确认项、未确认项和停止原因
```

让两个子任务分别报告“甲可行、乙读取失败”，再把回执顺序反过来，最终事实集合应相同；若结论变化，优先查是否依列表下标合并或使用“最后写入覆盖”。事件到达顺序可以影响何时首次有用，不能自行改变事实身份。若父任务只允许一次输出，迟到回执保留在旧运行；若产品允许增量修订，要有显式版本和用户可见更新。两种都比后台悄悄改掉用户已经看过的报告容易验证。

架构比较时也要把这些义务放回试验。双 worker 比串行方案更快交付第一家，可能只是它提前发出了部分结果，而基线被要求等待两家。统一输出义务后重跑，再判断真实收益来自并行、策略更好，还是任务被悄悄缩小。

## 共享预算怎样分给父任务和子任务

设总工具预算为 5 次，父任务要用 1 次验证最终引用。若甲、乙两个 worker 各看到“整题剩 5 次”并自主消费，两者可能各执行 4 次；等它们汇总后再扣账，超额动作已经发生。可选择提前分配不相交额度，例如甲乙各 2 次、父任务预留 1 次；也可用中央计数器在派发每个动作前原子预留。前者容易验证与隔离，但空闲 worker 的剩余额度可能浪费；后者能动态共享，代价是协调与资源争抢。仅将相同的预算数字写入两个提示词，无法保证总体上限。

预算也存在归还边界。已预留但尚未发送的读取被取消，可以按政策归还；已发往下游却没有回执的调用，其真实消耗未知，不能假装从未执行。把工具次数、模型轮数、绝对截止和 token 分开建账，否则一个子任务可能在工具额度内耗尽全服务的模型配额。父任务收到“完成”时再收回未用额度，留下最后一次归并与事实核验所需的时间。这种设计把你熟悉的后端资源隔离迁移到了会自主决定下一步的执行者上。

## 面试推演：如何为子 Agent 的额外花费辩护

先提出一个可以推翻自己的对照。如果同一批已知 ID 用并发工具取得同等质量，且更多模型只增加时延、成本和不确定性，应保留普通工具。如果只在“分支内需要重新选源”的任务族里独立 worker 能在同预算内减少遗漏，那才有具体使用条件。报告应包括父子全部模型调用和 token、实际工具尝试、达成任务比例、最慢分支与取消后仍运行的工作。只展示父 Agent 从五轮减少到两轮，会漏掉被转移给子任务的十轮。

遇到反问“能不能让两个 Agent 辩论直到一致”时，可以指出他们可能共享相同盲点，而且一致本身缺乏外部证据。规定争议命题、可接受的证据、最大轮数和无法裁决时的交付形式，再讨论辩论是否比查一次权威资料有用。这样回答把多 Agent 的价值落在可验证的新增信息上。
