# 第 10 章　时延敏感的 Agent 应用：从用户等待的时钟推导优化

给一个 Java 接口做优化，通常会先看入口 P99，然后找耗时最大的依赖。Agent 请求更容易让指标说谎：它可以很早就返回一句“正在查询”，可以并行启动许多最终没用上的工具，也可以为了赶截止时间直接答“不知道”。三种做法都可能让某个时延数据变好，用户获得正确结果的时间却没有改善。本章从一次用户请求的事件顺序出发，把质量、成本和延迟放回同一张账单。

## 先确定时钟的两个端点

设客户端提交请求为 t0，收到首个 token 为 t1，收到第一条能回答用户问题且有证据的事实为 t2，收到经过校验的终态为 t3。t1 很早只能说明开始收到输出。对诊断类任务，“正在分析”没有减少用户对原因的不确定性；“在完整召回快照中找到目标 P7”则已经排除了“召回阶段完全没出现”这一种解释。两者的产品价值不同。对只读查询可以先流出已证实事实，对有副作用的业务则不能在数据库提交前向用户宣告“已完成”。

`t2−t0` 只有在实际出现正确事实时才有值。没有正确事实的请求不能塞成 0 ms。汇总时同时报告“在 800 ms 内得到至少一条正确事实的请求数/全部请求数”，并单列已有正确事实的时延分布。否则把失败的慢请求全删除，成功样本的 P95 会显得漂亮。对 t3 也类似，应区分响应已结束、正确完成、明确部分完成、超时和越权拒绝。阈值均须由目标业务给出或标清为实验假设。

**手算尾延迟。** 教学样本为 20 个请求，18 个在 400 ms 完成，1 个 1,200 ms，1 个超过 2,000 ms 截止。按 nearest-rank 算，19 个成功样本的 P95 是排序第 19 个，即 1,200 ms。全体“1 秒内正确完成”只有 18/20，超时率为 1/20。若把超时当作空值从分母剔除，看起来就成了 18/19。写清分位数算法、样本量与分母；少量试验要看明细，不能凭 20 个请求推断生产 P99。

教学例：100 次已发请求里，90 次在 2 秒内 complete，其中 8 次事实错；另有 5 次 partial、5 次超时。如果目标是“2.5 秒内正确完成”，达标数是 82，达标率为 82%。用 90/90 去算 HTTP 成功样本的平均时间，无法回答这个目标。再按查询桶检查 8 个错误集中在哪里，才能判断是哪条架构路径必须回滚。

## 顺着一次慢请求去找能缩短的等待

假设一次教学 trace 如下：网关排队 80 ms，初次模型推理 470 ms，工具 A/B 并发耗时 140/360 ms，最终模型生成 640 ms，校验和传输 50 ms。无其他重叠时，完整关键路径为 1,600 ms。把较快的 A 从 140 ms 降至 40 ms 不改变 360 ms 的汇合点，总耗时不变；若产品允许在 A 的事实独立核验后先发给用户，首事实有可能提前 100 ms。是否值得改，取决于要改善 t2 还是 t3。

常见模型服务可以粗分输入处理、逐步解码和队列等待。输入处理受提示长度和服务实现影响，长历史及重复注入大段日志会增加开销；生成冗长解释会增加输出 token 及解码轮次。若模型网关只给出客户端首 token 时间，不能仅据它断言“慢在模型计算”，因为建连、排队、服务端调度、网关缓冲都可能在内。采集客户端时刻、应用分段、提供商可见的 usage 与排队信息，再把观测不到的部分标为未知。跨机器 span 的相对顺序需要可比较的时钟或明确的因果链。

以地图日志分析为例，若用户只问“目标是否出现在候选阶段”，Java 可以按结构化 ID 在完整原文中检查，向模型返回对象、覆盖范围、判断和定位信息。比起整段日志送入模型，这会改变模型输入量和证据噪声。它的正确性条件是解析器确实扫到了对应阶段的完整集合；如果读取上限截断，只能标注“可见片段未找到”。比较优化前后时要保留这一覆盖指标，否则“提取摘要变快”可能只是少读了决定性证据。

## 等待最慢分支，尾部概率怎样累积

若各分支耗时互相独立，分支 i 在阈值 t 内完成的概率为 Fᵢ(t)，所有分支都完成才能结束，则汇合在 t 内完成的概率是各 Fᵢ(t) 的乘积。若十个分支各有 99% 概率在 t 内完成，至少一个超 t 的概率是 1−0.99¹⁰≈9.56%。这解释了为何单个工具看着很稳定，多分支比较任务却频繁碰到慢响应。实际系统可能共享连接池和模型配额，分支并不独立，因此要从请求级 trace 直接测联合分布。[The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)

“取最先成功的一个”会改变等待条件，不能把它当成无损优化。用户要“找出任意一家符合条件的场馆”，第一个经验证的可用场馆就够；用户要“在两家里挑更早关闭的”，必须取得两方可比较的时段，不能因为甲先返回便替它宣告胜出。工具的截止时间与返回义务要写在同一个终态条件里。若 B 超时，答复“甲已核实，乙尚未核实”可以是合格的部分完成，是否满足产品的完整成功标准须另计。

## 吞吐、并发和排队为什么会互相影响

在稳定系统、边界与单位一致时，平均在途请求数 L、平均到达率 λ、平均停留时间 W 满足 Little 定律 L=λW。举例：若稳定处理每秒 20 个用户请求，每个从入口到终态平均 1.5 秒，平均就有 30 个请求在系统里。这是平均数量，不代表 30 个工作线程就能满足 P99，也不说明模型并发槽够用。一条请求如果平均发起 2.5 次模型调用，平均模型调用到达率已是每秒 50 次；每次持有模型并发槽 0.4 秒时，平均需要 20 个忙槽。再叠加突发与慢尾，高利用率会带来额外排队。本例为容量演算，过载未稳时不能机械套用稳态等式估计等待时间。

闭环压测中，一个客户端做完上一个任务才发下一个；服务变慢会连带减少请求到达。要研究外部流量冲击，应按预设到达时刻发送并记录延后发起、入口拒绝与队列等待。区别类似工作日固定客流与柜台只放一人进来。若压测机已先耗尽线程或连接，观测到的瓶颈便混入客户端能力，所以要同时报告计划发起数、实际发起数和完成数。[Google SRE 对时延、流量、错误和饱和度的说明](https://sre.google/sre-book/monitoring-distributed-systems/)

## 按瓶颈选优化：缩短路径、减少输入或隔离资源

若耗时主要来自第二次模型往返，而答案的所有字段已经由工具确定，可以对满足充分条件的请求用结构化模板完成最后一步。验收要检查范围、事实和用户意图能否由模板完整表达。若耗时来自大提示，先保留用户目标、动作所需字段、对象与来源，删除不能影响本轮选择的历史，再用一组跨轮指代和罕见约束做回归。若慢在工具下游，缓存只读且有版本的结果；缓存键至少包含对象、权限范围、主题和资料版本，命中后仍需核对本轮问题是否相同。

缓存命中率本身不是成功指标。考虑冷缓存时两百个相同请求同时到来。只做 Map 缓存时，所有请求读到 miss，可能同时打穿下游。可以对同键合并正在执行的只读操作，让等待者共享一个 Future；当一个等待者退出时，应避免误取消仍被其他请求需要的底层操作。共享键若漏掉租户与权限，就会把性能技巧变成跨账户数据泄漏。Java 工程里常用的超时、线程池隔离、请求合并都适用，但要针对 Agent 的多轮、工具扇出与证据范围重新检查前提。

若慢在共享模型排队，减少并发扇出、区分交互请求与后台分析、限制队列长度、在总 deadline 不足以产出有用事实时早点返回可验证的部分结果，都可能比增加模型实例数更便宜。服务端拒绝要明确记录为未完成，不能因为快速结束计入正确完成率。平台费用则至少分输入 token、输出 token、工具或外部 API 代价，并按**每次正确完成**和**每个尝试请求**两个口径报告。

## 用同一条 trace 判断该优化模型、工具还是证据传输

下面是另一个教学例。用户请求解释目标 P7 未入最终页，原始诊断资料较长。系统先读完整输入，再提交摘要给模型。两次执行的用户目标相同，模型版本也相同，第一条资料覆盖全量，第二条只覆盖截断片段。若只看“输入从 12,000 token 降到 1,200 token”，可能以为后者是优化成功；如果判分表却显示第二条开始编造“被过滤”的结论，就应把覆盖范围作为质量约束，查压缩逻辑删除了哪项证据。性能实验应当能检测变快的错误答案。

把一个请求拆成可比较的四段。第一段是应用排队和取得原始资料，第二段是 Java 解析与选择证据，第三段是模型排队及生成，第四段是规则校验与输出。如果第二段从 70 ms 降到 15 ms，但第三段在共享模型队列增加 200 ms，用户总等待可能上升。反之，哪怕第二段多花 20 ms 做结构化提取，只要省去一次长上下文推理并保留决定性证据，整体可能下降。每次实验仅改变一个因素，并保存同一请求的前后分段，否则无法区分优化收益与提供商波动。

成本也可做一道独立检查。教学假定 A 每次尝试花 0.10 单位，100 次中正确完成 80 次；B 每次花 0.08 单位，100 次中正确完成 60 次。B 的单次成本确实便宜 20%，但每次正确完成的成本 A=10/80=0.125，B=8/60≈0.133，B 反而更贵。两个数字用途不同：每次请求衡量花费速度，每次正确完成衡量业务产出；硬性越权和不受支持的断言仍要单独计数，不能靠平均成本折抵。

最后把“哪里该开始打点”落在能运行的程序上。课程的压测探针在客户端校验期望事实和终态，适合发现首条正确事实和完整正确响应的区别；它不了解服务端的模型队列或内部工具时延。给请求分配稳定 trace ID，同时收集服务端跨度，才能在一条慢请求上对齐外部体验与内部原因。模型提供商未暴露的时间不要拆成虚假的精确子项，写为不可进一步区分的等待。[课内压测探针](../../bench/load_probe.py)

## 模型调用有波动时，怎样设计可信的 A/B 压测

同一接口在不同时间段可能受到共享限流或上游队列影响。先跑一小时基线、第二天跑一小时候选，模型端当天的负载差异就可能被误记为优化收益。可以在预算允许时交错运行 A、B，按任务类别、提示长度、输出上限与缓存温度配对或分层；控制各策略的并发份额，避免它们互相抢占到失去解释力。再用可重复的模型回放隔离本地队列、序列化和策略路径，最后以真实模型验证离线无法代表的部分。

同时给出失败与不确定区间。方案仅有十个样本且其中一条慢十倍时，先画逐请求耗时和原因，不要只留下一个 P99。若优化涉及按键合并、缓存或流式早发，给每一种机制配一个应当失败的反例：不同租户同参数不得共用私有结果、版本变化必须让旧缓存失效、未验证的事实不得提早发送。性能回归和质量回归一起跑，才可能解释某项改善究竟来自更高效的同一行为，还是来自少做了用户要求的工作。

## 面试推演：P95 好了，为什么暂缓发布

一组教学数据中基线和候选各有 100 次尝试。候选的成功请求 P95 更低，但有 7 次超时和 2 次未经证据支持的“已提交”。你的第一问应是指标分母和业务硬条件。若 2 次错误承诺属于不可接受写入结论，候选不能仅靠时延获准发布。接着按输入类型、冷暖缓存与负载分桶，看尾部改善是否只来自简单题比例变化，核实错误承诺发生在流式早发还是终态验证。最后明确回退开关、能够执行回退的人或组件、要监控的错误与截止内正确完成指标。

若被继续追问“用多少个样本才能宣布生产 P99 好了”，不要给一个脱离业务的万能数。先写分位数算法、负载分布、请求是否独立、分桶后的样本数和置信区间或分批重复结果。十几个真实模型请求适合展示分段明细；回放能低成本施压和验证排队机制，真实模型仍需验证提供商限流和生成长度。能区分这两类证据，你就能把后端性能经验转成对 Agent 服务质量有意义的结论。
