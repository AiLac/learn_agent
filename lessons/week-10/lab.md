# 第 10 周 · 实践讲义｜测量并优化搜索 Agent 的尾延迟

## 老师先读一行压测结果

假设某请求在 300 ms 收到提示文字，750 ms 收到能回答问题的正确事实，2400 ms 正确完成。目标若为 800 ms 内首事实、2500 ms 内完整正确，该请求两项均达标。现在只换成错误引用，文字与耗时全相同，首事实与完整正确都不应达标。这里的数值仅用于讲解，实际报告读取探针输出。

对照 JSONL 的 `first_usable_ms`、`terminal_ms`、`correct`、`outcome` 和汇总中的 `attempted`。对于未收到正确事实的样本，其首事实时延为空；计算“在阈值内取得首事实的用户比例”时应保留这个请求在分母里。再从逐行记录重算一次达标数，确认自己读懂了探针的口径。

## 1. 定义负载与观测点（1.5 小时）

从第 9 周选择一个基线和候选，例如固定流程与按请求路由。复用同一流式 HTTP 接口、模型标识、机器、证据快照和请求顺序。记录每段队列等待、模型调用、证据读取和降级原因。冻结一组业务质量题。与同伴约定目标流量和 SLO；缺少真实目标时，采用理论课示例并在报告中标为教学假设。

仓库提供[开放到达率探针](../../bench/load_probe.py)和[4 条冒烟题](../../bench/smoke-cases.json)，只需要 Python 3.10+ 标准库。服务由你在第 9 周实现。探针定时发起请求，记录客户端收到匹配 `fact` 与 `done` 的时间。`fact` 需含 `room_id`、`field`、`value` 和 `evidence_ids`。示例 ID `E06-nov-sat` 指第 2 周卡片，`registry:E06` 指名录记录；ID 不同时在题集登记等价的合法引用。参考答案只在施压端评分。

## 2. 做一次可解释的基线压测（2 小时）

从仓库根目录，在 Windows PowerShell 运行。第一次用回放的模型与固定工具时延验证流水线；真实模型单独跑小流量、限额的实验。使用不同文件名保留每个版本。探针每个请求新建连接，反映含建连的客户端体验；生产长连接、网关缓冲和用户网络需要在对应环境分别验证。

```powershell
py -3 bench/load_probe.py --url http://127.0.0.1:8080/search --strategy fixed --rps 2 --seconds 30 --workers 16 --deadline 6 --out runs/fixed-smoke.jsonl
py -3 bench/load_probe.py --url http://127.0.0.1:8080/search --strategy routed --rps 2 --seconds 30 --workers 16 --deadline 6 --out runs/routed-smoke.jsonl
```

先确认不同桶都发出且事实可判，再用 `--cases` 指定更大的公开数据题集。预热后分档提高到达率；每档分别记录冷缓存和稳定热缓存。相同查询顺序、缓存初态和并发限制下重复各档。4 条题重复 60 次只是链路冒烟。要解释 P99，应在预算允许的回放环境收集足够多的样本（例如每组数千次并重复批次）；真实模型样本少时直接列单次数据或分母。

## 3. 找瓶颈并只改一个因素（2.5 小时）

挑一个慢请求画出与服务端 trace 的对应关系。比较请求等待模型、排队、两馆工具汇合与最后生成分别用了多久。假如详情其一早已返回，另一项工具阻塞了全部输出，可以先流出已核实事实；假如连第一条证据都慢，先处理队列或取证。选择一种改动后原样复跑基线与候选，再看质量。对慢下游和缓存版本更新各做一次故障实验，检查是否超出总截止、是否产生旧时段断言。

## 4. 按分母作上线决定（2 小时）

- 探针打印 `offered`、`loadgen_dropped` 和各终态计数。施压端丢弃表示发生器没有空闲槽，与服务端拒绝是两件事；先检查 `start_lag_ms` 和施压机容量，再解释吞吐。
- `first_usable_ms` 只统计出现与参考事实匹配且带有效证据 ID 的样本；`terminal_ms` 包含收到 complete 或 partial 事件的样本；`attempt_end_ms` 包含已发请求的等待、失败与超时。探针发送 `X-Request-ID` 并把它写入逐请求输出，可与服务端轨迹关联。`first_within_slo` 和 `correct_within_slo` 分别是达标数，阈值可通过 `--first-slo-ms` 和 `--complete-slo-ms` 覆盖。逐行用“`correct` 且 `terminal_ms <= 2500` 的数量 / 已发数” 检查示例完整正确目标。首事实达标率同理，缺失计未达标。若目标要求 99% 在 5 秒内收到完整终态，须筛选 `outcome == complete` 并按已发数计算，不能用含 partial 的终态分位数替代。单独报告部分答复和拒绝，另给以提供负载为分母的成功率。
- 自动评分只核对题集列出的字段及允许的证据 ID；完整中文简介、额外事实和证据原文仍用第 4 周方法人工抽查。替换为真实断言和业务权重后，才能讨论实际 SLO。

| 报告最小字段 | 每组填写实测值 |
| --- | --- |
| 环境和负载 | 策略、模型或回放、题集、缓存初态、目标/实际 RPS、样本数 |
| 体验和质量 | 首事实覆盖率与 P95、完整正确达标率、终态 P95/P99、超时/部分/错误数 |
| 代价与决策 | 模型与工具调用数、每正确完成一题的 token 或费用、哪个查询桶回退、回滚条件 |

**验收。** 提交同负载的前后对照、一条关键路径、一次失败或过载时的降级证据，以及“哪些查询采用优化、在什么条件下回滚”的具体决定。回放或本机测量要明确标注环境；没有用户流量的结果按实验表述。
