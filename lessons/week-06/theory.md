# 第 6 章　MCP、故障恢复与信任边界：从一次 Java 调用追到另一个进程

原来 `lookupHours(place)` 是 JVM 里的方法。把它交给另一个进程，用 MCP 暴露给多个 Agent 客户端后，业务代码几乎没有变化，故障空间却扩大了：两端版本可能不同，服务器可能启动但未加载快照，一次读取可能已执行而回复还没到。一个做过 RPC 的工程师已经有了合适的直觉。这里要补上的一层是，执行结果还要变成下一轮模型能理解、能关联、不会被误用的观察。

## 顺着一个请求分清四个角色

宿主运行用户会话、维护工具权限、调用模型。在宿主内部，MCP 客户端负责和某个 MCP 服务器通信。服务器公布工具并执行请求；模型则根据宿主提供的工具描述提出调用意图。模型通常不持有 stdio 管道，也不会自己执行 JSON-RPC。宿主可把某个已发现的工具包装成原生模型函数并取一个适合模型选择的名字，之后再把提议转成 MCP 调用。因此服务端的工具清单、实际暴露给模型的清单、当前用户有权执行的清单可能不同。

对熟悉网关和 RPC 的读者，`tools/list` 有点像接口发现，`tools/call` 像一次方法调用，但发现成功只说明对方描述了能力，不能证明资料已加载、后端依赖健康、当前用户获准读取。课程固定使用 MCP 2025-11-25；说明协议时应写版本，避免把某个 SDK 当时的实现等同于协议本身。[生命周期规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle) · [工具规范](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)

逐帧看一遍本地程序。客户端发送带请求 ID 的 initialize 并声明支持的协议版本与能力，服务端用相同 ID 应答所选版本和其能力。客户端接受后发出无 ID 的初始化完成通知。下一次 tools/list 返回工具名与参数模式，最后的 tools/call 携带真实参数。stdio 示例用一行传一个 JSON 消息，服务端的标准输出只写协议数据；若把一行调试日志写进去，客户端在解析那一行时就会失败。业务工具可能从未收到请求，错误应落在传输/解析层。[课程本地客户端和服务端](../../examples/mcp/roundtrip.py)

```json
{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"lookup_hours","arguments":{"place":"E06"}}}
```

模型一侧的调用 ID 可以是 c7，MCP 一侧是请求 3，业务对象是 E06，资料是 hours:E06。宿主应把四者映射到同一条 trace。多个模型轮次共用一个连接时，连接标识只能说明流量经由哪个客户端；它无法天然证明这个请求是父 Agent 还是子 Agent 发起。若产品要禁止子 Agent 调 MCP，最直接的做法是不给子运行时这个客户端或工具，再检查执行端是否还能从其他路径派发。若执行端必须区分委托身份，需要有可信的逐调用凭据和授权校验。某个模型自报 `agentRole=child`，或在提示词里写一句禁用，不能构成安全边界。

## 为什么 HTTP 成功同样可能没有业务事实

把这个区别套进地点问题定位，更容易发现错误。一个接口成功返回“0 个候选”，调用方得到的是有效的空业务结果，应该继续判断是用户本来不该有结果，还是某环节缺失。若接口超时，连“候选数为零”都不能断言。工具外层请求成功但内部返回执行错误，又是第三种状态。模型下次动作用的是业务观察，宿主应先归类并保存原信号，再将能安全传达的部分转换成观察。

| 所见信号 | 可以确认 | 仍未知 | 下一步举例 |
| --- | --- | --- | --- |
| 合法业务体且候选数组为空 | 这次已完成查询在指定集合内没有候选 | 是数据问题还是符合预期 | 检查查询范围与用户预期 |
| 工具结果含执行错误 | 已取得错误回执 | 目标事实是否存在 | 按错误性质修正参数或降级 |
| JSON-RPC 拒绝未知工具名 | 这条协议请求未按该名字执行 | 其他合法工具是否可用 | 核对协商版本和名称映射 |
| 客户端到期无完整回执 | 当前等待已结束 | 服务端是否执行、副作用是否发生 | 读可有界重试；写先查状态 |

课程示例的 NO_DATA 放在成功的业务体里，故意使用未知工具名时得到协议错误，额外字段会触发示例工具的参数错误。这是帮助学习的固定实现；编写通用客户端时，应查看收到的错误层级和协议的具体约定，不能仅靠错误文案做重试决策。

## 重试次数、截止时间与副作用要用一份账算

设总预算 1,000 ms，已经用掉 400 ms，最终整理和返回预留 150 ms，最多还剩 450 ms 给工具、排队及退避。某工具的单次超时设 300 ms，若第一次耗满，剩下给重试的有效额度最多 150 ms；如果还要退避 80 ms，再发一个 300 ms 请求就已违反总时限。绝对截止时刻在同一进程可由单调时钟计算，跨进程传播时要明确剩余时长或约定的截止表示，不能直接相减两台机器各自单调时钟的读数。一次超时的读请求也可能消耗下游资源，重试要计实际尝试。

若模型循环最多尝试 3 次、SDK 每次最多再尝试 3 次，下游最坏会收到 9 次调用。重试所有权分散还会让每一层都以为自己遵守预算。将瞬时网络重试放到一层，保留同一业务意图但给真实尝试独立标识，上层根据剩余总预算决定是否改策略。对写操作，能否重试由第 2 章的幂等能力决定。用户取消与下游响应也存在竞态：发送取消请求只能说明表达了取消意图，无法证明远端尚未提交。

## 恢复到底从哪里开始

把一条操作拆成五个事件：宿主接受提议、记录待派发、发给下游、收到回执、把观察纳入模型历史。若在第二与第三步之间宕机，恢复者可能不知道网络发送是否发生；若第四步后已持久化观察，但第五步没做，则可以从观察重组模型输入，无需再执行读取或写入。恢复不是简单让模型“接着想”，因为它无法从半截自然语言里推断哪个副作用已落地。

对稳定、只读的快照，可按意图、对象、参数、快照版本复用结果。对外部写入，先以业务键查状态；本地事务和外部副作用如果不能原子提交，就必须接受存在“不确定”状态，并规划核对或补偿机制。若协作框架替你保存了消息检查点，也只证明状态写入了框架存储，不能替业务数据库出具执行凭证。

## 对照两种源码设计

Spring AI 的工具执行管理器从模型消息里提取工具请求并组装回传历史。LangGraph 的 `ToolNode` 处在状态图节点里，读 `_run_one` 和 `_execute_tool_sync`，找出工具选择、异常处理、消息封装三处。思考：如果 SDK 已经将异常变成工具消息，你的业务层再捕获和重试，会不会把它算成一次成功、或启动第二层重试？[Spring AI 源码](https://github.com/spring-projects/spring-ai/blob/9993102c830c132b88cb6857c0cdf41a22747432/spring-ai-model/src/main/java/org/springframework/ai/model/tool/DefaultToolCallingManager.java) · [LangGraph 源码](https://github.com/langchain-ai/langgraph/blob/e5e37b5d70dbfd93c7006bd90a658c6179a95946/libs/prebuilt/langgraph/prebuilt/tool_node.py)

## 为什么不要把 RPC 重试和重新问模型写在同一个 catch 里

设请求流程为 `模型 M1 → 工具 c7 → RPC id=3 → 资料服务`。工具服务在 130 ms 后回了业务成功，返回帧丢失。宿主看见网络超时，如果整个外层函数进入 catch 并重新从 M1 开始，模型也许改选另一个工具或新的案件。此时日志只写“第二次重试成功”，实际上你既改变了动作又改变了下游请求。原来那次操作是否完成已经无法从两条模型消息中推断。

更便于诊断的设计是区分三类标识：业务意图持有跨尝试稳定的操作键；一次模型提议有自己的调用 ID；每次传输尝试还有各自可关联的请求 ID。只在传输层重试时，沿用同一业务意图和模型提议，新增传输尝试。若观察确实改变了策略，例如服务明确报告主题不支持，才让模型提出另一动作，并记录新行动的理由类别。不必保存模型的内部思维过程，仅保存“源 A 不具备此字段，所以转用源 B”这种能由观察支持的决策依据。

同一思路解释为什么某个宿主里“服务可发现”与“子任务实际用到了服务”要分别验收。握手和发现成功后，主任务可能仍未传递选好的工具，子任务可能使用另一个连接，或者模型根本没发函数请求。要定位问题，就观察四个点：宿主交给本轮模型的工具清单、模型返回的调用意图、客户端发出的 RPC 请求、服务器的执行与回执。最早缺失的那个点决定下一步查适配层、授权、传输还是工具实现。没有第四项日志时不能从一句自然语言结论推断某工具一定执行过。

最后把安全与错误报告连起来。服务端返回的错误文本也可能含上游原文、文件路径或不可信指令。可以保留受控的错误类型和定位号用于追查，给模型返回经过裁剪的解释。若模型只需要知道“无权读取”，不必把内部异常栈、凭据或其他对象的字段加入上下文。这既降低泄露风险，也防止模型根据无关内容产生新的错误动作。

## 工具目录变更后，如何保持已经开始的对话可解释

一个常被忽略的故障是参数演进。第一轮列表宣告 `lookup_hours(place)`，模型据此产生提议；部署后工具把输入改为 `place_id,date_kind`。即使双方传输层仍能通信，这次请求也可能被拒绝或采用意料之外的默认值。对运行中的任务记录工具名和模式版本，保持兼容读路径或在版本不匹配时显式拒绝。重新发现工具后，若需要模型改提议，就把清楚的能力变化送入下一轮，不要在适配器里猜一个对业务敏感的默认日期再执行。

同样的版本意识也适用于回放。一年前的记录里 `holiday=null` 可能表示“未知”，新版若直接解释为“非节假日”，同一份轨迹会给出不同结论。恢复时用能解读旧版本的适配器，或明确定义迁移并保留原始版本信息。模式兼容可以通过固定输入输出样本测，业务语义兼容还要变换用户目标、日期和证据范围进行测试。协议打通是互操作的第一步，无法单独验证业务语义。

## 面试推演：子 Agent 要复用公共工具，服务端能认出它吗

设主、子运行时共用同一 stdio 连接，服务器每次只看到工具名与参数，没有可信的调用者身份。即使日志含同一个会话标识，服务器也无法可靠裁决“只许主 Agent 调用”。可选设计一是每个角色由宿主组装不同工具集合，子任务只接收主运行时裁剪后的数据；设计二是独立连接并绑定不同身份与能力；确需共享连接又要执行端验证时，传递可验证且受时效、作用域约束的逐调用授权。哪一种合适取决于谁可信、谁能发包以及哪个组件承诺阻止越权。

追问“怎么验证”时，不妨提出一组可证伪的实验。主任务正常读表应成功，子任务直接调用应被执行边界拒绝，伪造角色字符串也应被拒绝；超时重放须符合业务幂等规则。成功一次握手或列出能力，都没有验证这四件事。这个答案同时保留了协议的用途和协议本身没有替应用解决的责任。
