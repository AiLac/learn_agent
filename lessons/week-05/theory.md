# 第 5 章　Agent 怎样记住一段对话，也怎样正确地忘记

第一轮用户问花园街周六晚上是否开放。第二轮他说“那第二家周日呢？”后端眼里只有九个字，缺地点、时刻、月份，还带一个依赖屏幕顺序的指代。模型可能读懂中文，却无法从这句话唯一恢复用户指的地方。假如后台只展示过一家，最合理的结果甚至是追问。记忆设计的起点，是弄清**后续决策需要恢复哪些事实，它们各自以什么为依据**。

## 对话记录、任务状态、外部事实分别能回答什么

聊天记录支持回答“用户曾经说了什么”，任务状态支持回答“当前有效约束是什么”，外部证据支持回答“这个业务对象在什么条件下有什么属性”。这三类信息可以都存数据库，但更新与失效条件不同。用户说“还是上次那家”，需要参考先前会话；用户说“我刚上传了缺件”，新的外部事实却可能推翻同一段对话的旧观察。把历史摘要写成一段“用户资料完整”，不附案件、时间和来源，程序既无法安全重用，也难以纠错。

短期工作记忆可以是本次目标、剩余预算、已展示对象和待补字段。跨会话记忆适合保存用户明确且可持续的偏好，如偏好先展示已核实结果。一次“这周只想找晚上开放的”带有时间限制，不能永久提升成用户画像。事件记忆记录过去发生的事，例如某次工具超时；语义记忆保存可以反复使用的知识，例如某版本常规时刻表。前一次超时不能当成该馆永久不开放。分类的用途是决定写入政策、读取范围和删除条件，无须为每个名词采购不同的存储系统。

## 一句追问如何变成可审查的增量更新

| 字段或信息 | 第一轮 | “那周日呢”之后 | “换成油麻地”之后 |
| --- | --- | --- | --- |
| 分馆 | E06 | 沿用 E06 | 更新为 E01 |
| 适用月份、时刻 | 11 月，19:00 | 沿用 | 沿用 |
| 星期条件 | 普通周六 | 改为普通周日 | 沿用周日 |
| 结论的支持证据 | E06 周六 | 重新选择 E06 周日 | 重新选择 E01 周日 |

用 Java 接口设计眼光看这个问题，一个可空字段不足以表达“保留、删除、替换”。可以使用带类型的补丁，例如 `Keep`、`Clear`、`Set(value)`。用户说“周日呢”只对星期发 Set；“时间不限”给时刻发 Clear；“还是那家”保留地点。如果把反序列化后所有 null 都当清空，改星期的请求会把对象一起删掉。如果把 null 全当保留，又无法表达用户主动撤销要求。让模型提出补丁，再让纯函数应用它，既保留语言弹性，又能脱离模型单测状态演变。

展示顺序值得单独记录。内部按新策略重排后得到 [D07,E06]，用户上一轮看到的却是 [E06,D07]。“第二家”绑定到当时用户能看见的快照 D07；不能重新跑一次排序再取第二项。若两轮之间客户端切换了列表，可以使用显示批次 ID 和所选行 ID 还原指代。把这种错误归到召回效果会让工程师调错系统：数据和排序可能都正确，丢失的是交互状态。

## 有限上下文怎样分配给记忆

上下文窗口是本次模型输入和输出能使用的有限容量。存储层中有十万条历史记录，不意味着一次推理应看见十万条。上下文组装器要做的是在预算内选择满足本轮推理所需的材料。承担事实证明的原文和适用条件，应优先于无关的历史寒暄；覆盖用户刚更改约束的补丁，也比一段很早的摘要更重要。相似文本检索可用于找候选记忆，但还要按主体、时间、对象、版本和目的过滤。

做一个预算题。假设模型总窗口 8,000 token，预留输出 1,000，系统规则与工具模式占 1,500，当前用户问题和结构化状态占 500，那么至多还有 5,000 可放历史与证据。若两张卡各 600，候选摘要共 900，还剩 2,900。此时加入 3,200 token 的旧聊天全文就会越界。一个办法是只摘取其中与“第二家”有关的显示批次和用户原话，同时保留可回查的位置。这个操作虽然节省空间，却带来信息丢失风险，必须用后续指代与撤销用例验证。具体数字仅作计算练习。

上下文够长也不必然用得好。在长文档问答研究中，有实验观察到相关信息所处位置会影响特定模型和任务的表现；不能把这个实验证明扩大为所有当前模型都遵从固定位置规律。对自己的应用，做一组内容相同但排列不同的输入，在开头、中间、末尾放同一关键约束，看任务结果是否改变。若改变，再评估按任务组织上下文、压缩非关键历史或显式传入结构化状态。[Lost in the Middle 原论文](https://arxiv.org/abs/2307.03172)

## 一份记忆何时必须失效

用依赖图思考结论缓存。结论“周六 19:00 可以去”依赖地点、服务区域、日期类别、时刻、证据版本与所问属性。用户仅改星期，证据卡本身可能仍然有效，因为它保存整周时段；已计算的结论和所选星期切片必须失效。若换场馆，原卡不再适用；若问实时余座，原数据源甚至不提供这个属性。凡是只用问句文本作为缓存键的系统，都会在“那周日呢”这种跨用户短问上受到挑战。

| 本轮变化 | 仍可复用 | 要重新计算或重新读取 |
| --- | --- | --- |
| 时刻由 19:00 改为 16:00 | 对象与同版本常规时刻表 | 是否开放、最终解释 |
| 用户选了展示列表中的另一家 | 当前月份、时刻与时间区 | 目标场馆的资料及引用 |
| 收到材料版本更新事件 | 用户检查缺件的目标、审批权限的可信来源 | 缺件差集、待提交草稿的前置条件 |
| 新会话只有“上次那家” | 经授权且能唯一定位的历史偏好或记录 | 跨会话指代；不唯一时需追问 |

对于可能包含敏感材料的记忆，先限制能读取的会话和主体，再给模型组装上下文。已经送给模型的内容无法通过事后的输出过滤“取消披露”。用户要删除某个记忆项时，需要考虑原始记录、摘要、索引和衍生缓存是否仍能把它重新引入。数据生命周期是内存设计的一部分，和窗口长度是两个不同维度。

## 恢复、并发与合并的陷阱

设同一会话版本 7 同时收到两个更新。A 把星期改为 SUN，B 说“第二家”，其指代依赖版本 7 的显示顺序。若两者整行覆盖，后提交者会丢前一项更新。使用版本条件写入后，一个更新成功，另一个检测到冲突。能否自动重试取决于补丁语义：给独立标志设值可能安全；“第二家”则要先确认显示批次是否仍然成立。重新读取当前版本并机械应用原补丁，不保证尊重了用户当时的意图。

图框架的检查点可以保存某个线程或会话在若干步骤之后的状态，使故障后不必从第一轮重新推断。它不能自行判断外部世界是否在暂停期间改变，也不能把任意外部副作用变成幂等。恢复后要重新验证授权、已过期的数据和待执行写入的前置条件。读懂检查点保存了什么、重启时从哪一边界继续，才谈得上持久化。[LangGraph 持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)

## 大日志不进提示词时，怎样保证模型还能核对原文

对有地图检索调试经验的工程师，上下文问题最直观的形式是：一个请求的 debug 文本可能远大于这一轮可合理送给模型的内容。第一种简单做法是截前若干字符，第二种是让模型先摘要。前者会偏向日志最前面的阶段，后者可能丢掉“只记录前 K 项”和“字段没写入”这样的关键限定。两者都可能让系统得到一个看似肯定的缺失判断。

可以让只读解析器持有完整输入，向模型暴露按目标和阶段读取的工具。第一轮只返回 `stage, observedCount, scope, targetStatus, evidenceRef`；需要核对异常时，再按引用取窄窗口原文。如果输入是增量片段，还要带文件版本或内容摘要、完整性标志。引用只标字节偏移时，原文更新后偏移可能指向别的内容；引用同时绑定版本，才能保证下一轮看到的是同一证据。解析器若遇到未知结构或读上限，应返回“未完整扫描”，让模型知道后续动作是换方法或保留未知。

这种模式可以理解为记忆的分层。原始观察保存在模型外，任务状态保存“已核对哪些范围”，上下文只带对下一步决策有用的材料。RAG 在这里帮助按需取内容；是否要取、取哪个阶段、何时停止由策略决定。若每轮都取回同一段优先级最高的材料，还需要记录已经检查过的范围，防止持续重复。面试里可以用一个具体边界说明收益：上下文变短是可量的输入减少；未丢证据还必须用截断、跨阶段同名字段及更换目标等独立样本验证。二者不能由同一张 token 账单证明。

## 摘要是一种有损状态变换，如何让它可复验

如果模型把“上轮列了两家，用户偏好第二家，周日再确认”压成“用户想了解附近自修室”，这段摘要在语义上相似，却已经不能回答下一轮的指代。一个办法是将摘要分成两部分：机器字段保存对象、显示批次、硬约束、被撤销项和引用；自由文本仅解释用户的偏好或尚未解决的疑问。生成摘要后，用几个固定探针查询“第二家是谁、哪个时段刚撤销、哪些结论需要回源”。若摘要无法正确回答，用结构化记录恢复，而非被迫相信摘要。

实际系统还要区分写入候选与事实。用户说“我猜那个场馆应该全天开放”，可以存为用户假设用于理解后续追问，但不得升格为场馆事实。工具返回“普通周日 09:00–17:00”时应并存来源与适用条件，允许覆盖旧推断却保留用户原话。对于相互矛盾的不同来源，先保存冲突及版本，明确需要更权威或更近的观察后再解除。对工作记忆作这个小小的证据分层，能同时减少重复查询和错误自信。

## 面试推演：把全文放进长窗口，能替代状态管理吗

假设用户随后说“取消刚才的时间要求，但继续看第二家”。请先不提向量库，直接算出补丁：清除时刻，保留目标服务，按原显示批次定位第二个对象，使依赖时刻的结论失效。然后再解释模型输入应包含当前目标、用户这句原话、展示映射和新的有效约束。若面试官进一步要求“同时处理两部手机发来的追问”，就补上会话版本、请求幂等键和冲突处理。窗口负责供模型阅读，状态更新负责确定哪次修改在业务上生效，两者共同工作。

换成商户预审再答一次。上轮记忆是“缺结算证明”，本轮用户说“刚上传，请再看”。用稳定偏好缓存回答会伤害正确性，新的外部事实必须重新核验。能主动解释哪项应记、哪项应忘、哪项必须回源，是这一章要留下的工程能力。
