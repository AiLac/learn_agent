# 第 4 章　怎样评测一个 Agent，以及如何用一次失败定位错误

你准备给团队演示新版 Agent。旧版答对 8 题中的 6 题，新版也答对 6 题。旧版遇到超时会放弃，新版能恢复，却曾在只读请求里创建草稿。究竟该说“没有改进”“有所改进”还是“不能发布”？这个问题不能靠换一个相似度指标解决。你首先要决定何为完成任务、哪些条件绝对不能违反，以及推断“某项修改有效”需要怎样的对照。

## 评分对象是一条执行轨迹及其终态

用户要求核实通常开放的时段。三个系统都答“周日晚上七点已关闭”。甲按时刻表查询并引用正确条目。乙在查询前直接猜中。丙查了同楼体育馆，再复述甲的结论。只比字符串，三者相同；若任务要求可核实，只有甲满足要求。相反，两个系统即使采取不同的合法行动，也可以都通过。你需要同时评价最终任务状态、必要前提和禁止行为，才不会把某条示范轨迹变成唯一标准答案。

一条评测题包括起始环境、用户目标、允许能力、完成条件和不能发生的变化。一次执行叫一次试验；完整轨迹记录动作与观察，最终状态记录实际发生了什么。写入类任务尤其要看最终状态。模型说“草稿已创建”只是一项文本主张，模拟数据库里到底是一份、两份还是零份，才回答了是否完成。

把题目“检查缺件，不要写草稿”写成一个可判的函数。输入有已收材料、所需材料和权限；执行后要从存储层读回实际状态。对这次运行，定义三个布尔量：是否指出正确缺件，是否保持草稿数不变，是否避免未经授权改变申请状态。只要禁止条件失败，即使中文说明写得完全正确，整题也失败。对“起草一份”的对偶题，要求恰好新增一份；若测试使用相同数据库，执行前要先记录基线或重置夹具。否则残留草稿会使后一次测试假通过。

评测记录最好并列三个标签。**任务结果**回答用户是否拿到正确成果；**保护结果**回答宿主是否阻止违规动作；**故障归因**记录首次可观察的偏差。模型试图写入但被宿主拦住，在保护维度可以通过，任务维度仍要看用户的只读查询是否有正确答案。违规提议率与违规执行率分别测决策和保护，分子分母都不同。这一点在面试里比报一个“安全率”更经得起追问。

## 确定性判分、人工判分与模型裁判的分工

| 情景 | 可自动判的条件 | 仍需人工检查的内容 |
| --- | --- | --- |
| 明确周日 19:00 | 对象 E06、取得适用证据、结论 closed | 是否明确“普通非节假日”而避免扩大为实时结论 |
| 时间缺星期，或工具超时 | 缺星期追问；超时时允许部分完成，肯定事实须有证据 | 追问是否只补关键字段；降级答复是否保留已知信息 |
| 草稿写入后丢响应 | 允许起草、同业务键只有一份草稿，申请状态仍待补件 | 草稿内容是否遗漏用户要求，文字是否扩大为审批通过 |

对于明确可检查的字段，写确定性程序。对于开放式解释，先写出评分量表，例如“说明已核实与未知两项各得一分”，给两个已经判过的样本作为锚点。模型裁判可以扩大人工抽样，但要先拿一批人工判分比较一致性；不能让同一份缺证据的输出仅凭写得像标准答案就获得事实分。

设计裁判要像设计业务工具一样，先写反例。答案写“表中周日至十七时”，标准答案写“17:00”，字符串不相等但事实一致。反例二：答案引用正确的快照 ID，却将体育馆的时段套给自修室。根据出现了 ID 就给分，会错误通过。可以先规范化时刻和对象，再检查引用的语义范围，最后单独评价解释是否让用户知道“普通时段”与“实时状态”的区别。

假定用 20 份人工已判样本审核自动裁判。人工判定 8 份应通过、12 份应失败；自动裁判正确放行 7 份正确答案，另错放 3 份错误答案。这批样本的放行精确率是 7/(7+3)=70%，对正确答案的召回率是 7/8=87.5%。整体对了 16/20，不代表错放可接受。如果三次错放都涉及越权，应该把这个维度从主观裁判中抽出来，直接读权限和副作用记录。数字是课堂构造的样本，只能说明怎样读混淆矩阵。

模型裁判还可能偏爱长答案、与参考措辞接近的答案或候选列表中的某个位置。一个可执行的检查方法是交换两份候选答案的顺序并隐藏版本名，观察偏好是否反转；再拿一批由人独立判过且有分歧的样本看裁判理由。对主观维度保留“需要复核”，同时报告进入人工复核的比例，避免把这部分请求悄悄从分母剔除。[Agent 评测实践](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

## 同一任务做三次，“至少成功一次”和“每次都成功”差多远

一个写代码的 Agent 可以生成三个候选补丁，再用测试筛出有效的一个。多候选能力有意义。面向用户的一次自动审批则要求每次执行都遵守限制，三个尝试中只要一次越权，就已经有后果。这两种产品不能用同一种“重复三次”成绩概括。

先做数学推导。在三次尝试独立且每次成功概率都是 0.8 的教学假设下，至少一次成功的概率是 1−(1−0.8)³=0.992；三次全部成功的概率是 0.8³=0.512。把第一次未通过的请求反复跑到得到理想结果，只展示最后一次，等于悄悄改变服务承诺。实践中重复结果常常相关，不应拿一个估算成功率直接套独立公式。可以先逐题保留每次结果，再按“至少一次/全部/首次”在任务上计数。报告中通常称前两者为 pass@k 和 pass^k，写明 k、采样办法和是否允许选择答案。

看一份无需独立性假设的真实计数方式（数据仍为教学例）。三道题各跑三次，结果分别为 111、100、000。九次尝试共通过四次，试验级成功率为 4/9；任务级“至少一次通过”为 2/3，“三次全部通过”为 1/3。三项都对，只是回答的问题不同。若用户实际只有一次机会，最贴近的是按真实尝试政策测首次或单次请求表现。若每次重试会写入数据，先设计状态隔离及幂等，再讨论多次运行的统计意义。

## 用配对实验区分“更会行动”和“工具变好了”

要测有界循环是否有价值，用相同输入、工具、数据版本、模型版本、预算上限和评分条件，比较固定工作流与按观察决定下一步的运行时，真实消耗另记。若连数据或工具同时换了，无法知道改变来自哪里。要测工具说明是否更清楚，则固定运行时，只换说明。离线重放同一个模型提议能测宿主修复，却无法证明新提示能让真实模型少犯错。

从同一份用户意图集合出发，给每道题的两个版本配对。设有 20 题，二者同时通过 13 题、同时失败 2 题、只有 A 通过 3 题、只有 B 通过 2 题。总分 A 为 16/20，B 为 15/20。最值得读的是出现分歧的五题：B 学会两类追问但丢了三类简单答复。若三道退化都来自相同的过度澄清规则，一个提示修改可能同时解释多个失败，不能把它们当三种独立原因。小样本下这种分析比声称某方案“提升百分之几”可靠。

配对还需要控制输入的环境。方案 A 取公开快照，B 访问更新后的接口，出现差异可能来自资料新旧。方案 A 最多两次工具调用，B 可重试六次，则测到的是“策略加预算”组合。做机制归因时同数据、工具、上限和模型；部署选型时可分别优化两者，再比较同一用户目标下的正确性和全成本。二者有不同研究问题，都可以做，但要分别解释。

## 从日志拿到能改变排查方向的证据

重放 `wrong` 时，第一步工具提议正确，第二步观察正确，第三步模型拟定的 closed 与区间冲突，第四步宿主拒绝。若总表只显示 REJECTED，你可能误以为验证器拦错了。找“第一处偏离参考条件的动作”，再分开判模型策略与宿主保护。换成 early，错误发生于取证前。换成 timeout，本轮没取得结果并非模型错误；如果模型随后直接宣布关门，才出现新的判断错误。

继续追问“是上下文缺失还是模型读错”。先看真实发给第二轮模型的消息中有没有目标证据；工具服务记录 FOUND 不能证明该记录进入了模型输入。若没有，故障在消息组装、过滤或截断；若完整输入里有，再检查模型提议与宿主校验的入参。对宿主复现，固定原提议并重放；对策略复现，则固定环境重新执行模型。后者即使与你第一次结果不同，也有价值，它揭示输出的不稳定性。始终只主张日志真正能区分的原因。

## 建一套能抓到“根因编对了”的检索诊断题

假设你要给诊断 Agent 出六道题，不能拿用户实际日志公开。可以用课程公开地点和手工构造的阶段列表，刻意让一次只变一个条件。第一对保持用户问法不变，工具分别返回“有效空结果”和“超时”。第二对保持目标 P7 不在可见列表，分别标记为完整集合和前两项。第三对保持模型候选结论相同，只把证据来源由此次运行改为另一次。若六题都只判“报告中有没有召回、排序这两个词”，这套题对真实风险几乎没有区分力。

对第二对，让评分器检查两个独立属性。第一，报告能否准确陈述“在可见范围内未发现”；第二，是否禁止把有限范围推成完整范围的缺失。对完整集合可以接受“在该阶段完整输出中缺失”，却仍不能无根据写成“由某条过滤策略导致”。评测目标从复述关键词变成命题支持关系，这种判分能够兼容不同的合理行动路径。某一方案先读来源再计数，另一方案把两项合成一个只读工具，两者只要满足同一事实与权限前提均可通过。

再做一次防止判分器偷看答案的检查。把参考根因或预期动作存放在施测端，Agent 只接收平常可获得的输入。不要把题库文件整份索引进工具，尤其避免文件名本身泄露“应当拒绝”或“ranking_bug”。同一个地点、多种改写和同一故障模板尽量归组，留出时按任务族切分。开发阶段已经用来调提示的样本，适合长期回归，不再充当未见题。这样得到的质量结果才能回答面试官真正关心的问题：当下一次反馈的表述和记录范围变化时，你的 Agent 知道自己还缺哪条证据吗？

## 从“哪条样例出了错”推到“试验能否支持我的结论”

如果你以前调过搜索排序权重，很可能习惯先冻结 Query 集，再看策略前后某个目标的名次。把这个经验迁移到 Agent 需要多加两层：相同 Query 可能多次走出不同动作；动作本身还可能改变后续可见世界。评普通排序时重放同一文档集通常没有副作用；评商户草稿时，第一次试验写入的一条草稿会改变第二次试验。要用独立数据库或重置夹具，让 A、B 从可比较状态出发，再把最终状态和调用成本一同采集。

再考虑抽样。50 条地点询问中 45 条为有明确星期的简单题，新版只要优化简单题，就可能把总体数字抬高，仍然一直做错“缺条件应追问”。报告微平均时，每道题权重相同；报告按任务族的宏平均时，先算各组表现再平均，两者回答不同问题。若有真实线上流量权重，可按真实比例另算，但同时列出低频高损失组的硬失败数。没有真实流量分布时就把题集设计权重写清，别让面试官把人工采样的准确率理解为线上覆盖率。

## 面试推演：如何证明优化没有把风险藏起来

**面试官给题：“新版本的成功率上升，但不再报告资料不足了。”** 先查分母是否漏掉超时与拒绝，再把任务分成“有资料可完成、缺条件应追问、无资料应说明未知”。给第三类也设置正向成功标准。若系统对未知题一律给肯定结论，应在事实支持与越权维度扣分。也要反向检查：若把所有题都答成未知，有资料题应当失败。这样评测才不会奖励乱答或逃避。

**继续追问：“能根据没有观察到越权就承诺安全率吗？”** 只能说明在指定题集、版本、权限配置和执行次数上观察到零次。给出覆盖了哪些越权意图、是否真正进入执行端、如何验证后置状态，再解释未测试面。独立留出的新任务用于检验迁移，已经用于修复的失败样本转入回归集。实际面试中拿出一条原始失败、一处修复与同条件复测，比引用教学算例作为自己的服务成绩更有说服力。
