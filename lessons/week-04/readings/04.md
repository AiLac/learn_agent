# 用配对实验限制归因范围

要修 Java 校验器就固定原动作回放。要评提示是否改善，就让真实模型重新选工具。
两者若混成一个成功率，读者无法判断实际改变的是策略还是运行时。

本篇用一个封闭的教学决策器说明这一问题。输入是宿主收到的记录，不保证每个下游字段都已经获准使用。前置检查未成立时，下游即使带着缓存值，也不能拿来作业务断言。

## 先解决一个具体问题

**换了工具、数据快照和模型后，怎样声称是架构带来提升？**

这一轮只支持整系统差异。
要隔离架构，把工具能力、题集、模型与资源上限固定。将不同架构各自优化后的部署比较作为第二项实验报告。


先取一个能走到「计入未见题对照」的输入：其余关键条件已经冻结、真实模型提出动作、任务族从未用于调试、关键事件均可追溯。
把这四个条件代回后文的图，前面各个拦截分支都未满足，最终才有“环境冻结且真实模型完成独立试验”这个判断。
还原这个现场时要分别问：哪些位来自可信状态，哪些只是在接口中出现、尚未获得解释资格的字段。


从上到下取第一条成立的出口。只改一个开关时，只有它之前的检查都未截断，该变化才可能到达真实动作。

“试验控制”的两种输入分别是“其余关键条件已经冻结”与“环境或资料随版本变化”。
孤立机制归因要保持其他条件可比。

“决策源”的两种输入分别是“真实模型提出动作”与“脚本重放固定动作”。
回放能验证宿主分支，不直接验证真实选工具质量。

“样本独立性”的两种输入分别是“任务族从未用于调试”与“同一任务族已经参与调整”。
留出任务与开发回归承担不同的评价职责。

“可复核历史”的两种输入分别是“关键事件均可追溯”与“关键事件记录缺失”。
看不见的事件不能被解释为从未发生。
