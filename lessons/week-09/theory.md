# 第 9 周 · 理论讲义｜为时延敏感的搜索请求选择 Agent 架构

## 黑板推导：请先画出谁有权决定下一步，再选框架

同一个问题有四种可以真正编码的控制方式。固定工作流的边由开发者预先写死，适合前提已知、规则完备的动作。路由器先判断任务种类，把一部分送去固定分支，剩余交给动态策略；它经济与否取决于误路由率和回退代价。ReAct 宿主在每次观察后重新请求模型，能处理途中发现的新缺项。Plan-and-Execute 先交付一份可验证的计划，执行时可以利用独立分支并行；条件经常变化时重规划也有代价。图是表达上述状态与控制边的一种结构，使用图框架本身不能说明系统更自治。

| 输入 | 第一份观察可能改变什么 | 先验证的架构假设 |
| --- | --- | --- |
| 已给 E06 和普通周日 19:00 | 时段只决定结论 | 确定性规则能否满足全部条件并省掉模型往返 |
| “周末那里能用吗？” | 对象或日期不确定 | 一次针对性澄清是否比多跑工具更省时 |
| 两处都要核实，乙资料缺失才换备选 | A/B 可并行，乙的下一步取决于观察 | 可执行计划加一次有界重规划能否减少串行等待 |
| 检查缺件并准备草稿 | 写权限和幂等条件改变可执行动作 | 路由误判时，独立的宿主授权是否仍能阻止写入 |

**手算一次选择。** 教学假设模型往返各 500 ms，工具 A 80 ms、B 120 ms，聚合 20 ms，暂忽略排队。固定已知参数并发取证约 140 ms。模型先计划再并行取证、再模型汇总约 1,140 ms。单 Agent 若第一轮取 A、第二轮取 B、第三轮答复约 1,700 ms。若模型一次请求已经能并列提出 A/B，动态方案的关键路径也会缩短，不能把 1,700 ms 当架构定律。真实比较要把解析、生成首个可用事实、超时与回退算在同一用户请求内。

**错误路由怎么救。** 快路径只有在对象、日期、事实范围等前提均已满足时才能交付。否则返回结构化的 NEEDS_CONTEXT 给上层；同一用户请求最多回退一次。回退继承剩余预算，保留已经取得且仍适用的观察。把快路径返回“资料不足”计作快速成功，会系统性漏掉复杂用户。

## 老师精讲：架构设计先看谁有权决定下一步

固定流程把选择写进代码，可预测路径和资源消耗；ReAct 允许模型根据一次观察再选工具，更能应付歧义，却引入串行模型往返；先规划再执行把依赖显式化，便于并发和失败汇总，但规划本身需要成本，也可能在第一份证据返回后失效。多 Agent 再增加了独立上下文、通信、协作与共享资源竞争。架构名字不能决定哪套最快，实际负载里各种类型的请求占比，常比单个复杂案例更有决定作用。

考虑一条低时延快路径：只有场馆唯一、字段已存在、来源版本适用，才能直接返回。任何一项不成立，就移交给可澄清或补查的路径。快路径的价值来自减少不必要的推理，风险来自错误接受本应追加查证的请求。必须单独统计这类误路由。

### 用数字决定先测什么

示意 100 次请求中，80 次是简单字段，20 次需要取证。若每个简单请求节省 300 ms、每个复杂请求因新增路由开销多 50 ms，平均每请求节省 (80×300−20×50)/100=230 ms。这个算式没有告诉你 P99 会不会变差，也没有扣除错误直出的代价。下一次实验要分桶比较尾部、质量和回退率，而非拿平均数直接决定发布。

## 把“哪种架构最好”改成按请求作决定

查分馆所属地区、核对晚上是否开放、比较两馆并处理一处证据缺失，这三种请求所需的信息不同。地址题读名录即可；时段题要在同馆服务区域和日期条件上核实；比较题的两次取证相互独立。若所有问题都进入相同的多轮模型循环，简单查询也会承担推理往返。反过来把所有请求都塞进固定步骤，遇到别名歧义或资料不足时，又容易选错对象或无法追问。

| 架构 | 谁决定下一步 | 花园街案例的收益 | 时延代价与失败方式 |
| --- | --- | --- | --- |
| 固定工作流 | 代码先取候选再取证、生成 | 路径稳定，容易回放与做容量估算 | 简单题可能多查；分支条件遗漏后无法自行修正 |
| 单 Agent / ReAct | 模型观察中间结果，再决定查证、追问或结束 | 初次检索歧义时可以重搜 | 每轮推理多一次串行往返；重复调用会消耗预算 |
| Plan-and-Execute | 先生成或编制计划，再由执行器运行并汇总 | 比较两馆时可同时取证，明确处理部分失败 | 规划和汇总可能比两次工具查询更慢；计划失效还需重排 |
| 分工式多 Agent | 协调者给各分支独立的模型上下文和工具权限 | 分支需要自行消歧、补证时可以独立探索 | 共享模型限流、上下文复制和慢分支均可能恶化尾延迟 |
| 按请求路由 | 轻量规则或经验证的分类器选择上述路径 | 明确 ID 与单字段查询走确定性回复，复杂请求进入查证流程 | 误路由可能在快路径上给出错误答案；要统计回退和路由自身的成本 |

## 找到关键路径，而不是把所有耗时加起来

假设一次比较请求耗时如下（仅供手算）：路由 40 ms、检索 120 ms、两馆证据各 320/500 ms、核验 30 ms、生成 650 ms。顺序取证共 1660 ms，并发取证理想为 1340 ms，节省 320 ms；若额外加一次耗时 500 ms 的模型规划，合计就变成 1840 ms。一个分支可以并行，不代表整个方案变快。先画出依赖，再标出各段可独立启动的时刻。

等待全部分支时，总时间受最慢分支影响。在一个简化例子里，两个独立分支各有 5% 的概率超某个阈值，至少一路超阈值的概率是 `1−0.95²=9.75%`。生产中共享模型、连接池和网络会让分支相关，具体分布必须实测；各阶段 P95 相加也得不到请求 P95。[The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)

## 选择一个生产候选

设计时先写出路由所需证据。例：“花园街在哪个区”能唯一解析 E06，目标字段存在，就直接返回带名录引用的事实；“附近还有吗”需要明确参考点和距离口径；扩展集能算直线距离，步行分钟数仍需路径数据。若误走快路径，回退应携带已解析的地点与剩余时限。给每个请求一个统一截止时刻，规划、重试、工具和最终输出共同消费它。过时的分支结果不能覆盖已返回的答案。缓存及路由变更应作为实验变量记录。
