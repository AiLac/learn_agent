# 第 9 章　固定工作流、ReAct、计划执行和多 Agent，应该怎样选

“实时请求采用哪种 Agent 架构？”如果没有先问用户在等什么、可用哪些工具、错误能否挽回，这个问题没有唯一答案。把需求换成两个具体输入会更容易判断。甲给出已知地点、星期和时刻，只要一个按表判断；乙要求解释“为什么某个预期地点没出现”，证据可能完整、截断或冲突。甲的下一步几乎不依赖模型想出新策略，乙则可能根据第一份观察改查另一阶段。架构差异首先是**谁在什么时候有权决定下一步**，其次才是框架和代码形式。

## 用同一接口容纳不同决策策略

设每个策略都接收用户目标、可用状态、相同工具注册表和同一截止时间，返回可追踪的事实、终态和成本。固定流程可直接调用解析器和核验器；动态循环每轮请求模型；计划执行先提出可校验依赖，再并行；分工式系统让多个局部决策者在各自上下文中行动。它们能够共享同一套权限、证据格式和业务验证器。若多 Agent 实验给每个子任务都另配一份工具预算，而单 Agent 只有一份总预算，测到的优势很可能只是花了更多资源。

| 架构 | 谁决定下一步 | 花园街案例的收益 | 时延代价与失败方式 |
| --- | --- | --- | --- |
| 固定工作流 | 代码先取候选再取证、生成 | 路径稳定，容易回放与做容量估算 | 简单题可能多查；分支条件遗漏后无法自行修正 |
| 单 Agent / ReAct | 模型观察中间结果，再决定查证、追问或结束 | 初次检索歧义时可以重搜 | 每轮推理多一次串行往返；重复调用会消耗预算 |
| Plan-and-Execute | 先生成或编制计划，再由执行器运行并汇总 | 比较两馆时可同时取证，明确处理部分失败 | 规划和汇总可能比两次工具查询更慢；计划失效还需重排 |
| 分工式多 Agent | 协调者给各分支独立的模型上下文和工具权限 | 分支需要自行消歧、补证时可以独立探索 | 共享模型限流、上下文复制和慢分支均可能恶化尾延迟 |
| 按请求路由 | 轻量规则或经验证的分类器选择上述路径 | 明确 ID 与单字段查询走确定性回复，复杂请求进入查证流程 | 误路由可能在快路径上给出错误答案；要统计回退和路由自身的成本 |

把 RAG 放回这张图。RAG 描述的是“取回外部资料供生成使用”，它可以是固定的先读再答，也可以作为 ReAct 的一个可选工具，还可以供多个 worker 共享。改用向量召回不会自动使固定工作流变成 Agent。对这个课程的工程师，优先复用已有地点工具，在相同输入和观察下改变决策者，才是在学习控制架构。若需要测检索质量，把它当成独立部件另做对照。

## 一个可计算的路由问题

路由是前置决定：让多少请求直接执行已知规则，让多少请求进入能澄清、补证或规划的路径。先定快路径的可接受前提。对象唯一、属性在已知集合、资料范围与日期匹配、请求无写入含义，这些条件都可验证才输出事实。若不满足，返回 NEEDS_CONTEXT 给上层并继承已用资源。路由器说“我有九成把握”，只是一项估计，不能跳过业务前提。尤其是审核场景，误入读路径可能只是变慢，误入写路径却可能造成实际副作用。

做一个假设 100 次请求的例题。70 次确实简单，30 次需要动态查证；路由器把 65 个简单题和 5 个复杂题送到快路径，其余 30 个直达动态路径。若后置条件拦回那 5 个复杂题，最终快路径正确完成 65 次，35 次使用动态策略，其中 5 次付了回退代价。假设路由 20 ms，快路径 80 ms，动态路径 600 ms，忽略排队则平均总耗时为 (65×100+5×700+30×620)/100=286 ms。对照全动态的 600 ms，平均节约 314 ms。若后置条件漏掉那 5 个复杂题，表面上更快，却有 5 个错误抢答。报告必须同时给出错误直出数与正确完成率。以上均为教学参数，不能作为上线性能数字。

如果用模型做路由，它自己也需要一次模型调用，20 ms 的假设可能站不住。此时可以先用便宜的确定性充分条件判容易题，再把剩余任务交给动态策略；或者直接复用第一次模型调用产生的解析结果，避免下一步重新解析。哪种合算，取决于真实易题比例、误路由率以及每次推理是否真的从关键路径省掉。

## 从 DAG 推出关键路径，而非把 span 列表相加

给每个阶段标注它依赖谁，最早完成时刻等于阶段耗时加所有前驱完成时刻的最大值。这个递推在没有资源排队时给出由依赖决定的最短完成时间。若两个阶段共享一个模型并发槽，必须把资源等待也算入真实轨迹。并行两次工具调用时，用户等的是较慢者；若产品允许只要第一家确认可用就回答，停止规则变了，现在等的是首个满足条件的分支。两种架构只有在回答义务相同的情况下才能比较。

假设一次比较请求耗时如下（仅供手算）：路由 40 ms、检索 120 ms、两馆证据各 320/500 ms、核验 30 ms、生成 650 ms。顺序取证共 1660 ms，并发取证理想为 1340 ms，节省 320 ms；若额外加一次耗时 500 ms 的模型规划，合计就变成 1840 ms。一个分支可以并行，不代表整个方案变快。先画出依赖，再标出各段可独立启动的时刻。

一种容易漏掉的延迟叫投机执行浪费。系统可以同时发起两个可能有用的只读查询，等路由确定后取消一条，平均时延可能下降，但下游已经消耗配额，且取消不保证撤回。对高成本模型或会写入的工具，这种做法的风险大得多。如果要做，至少应限定在可并行的只读动作、记录实际完成的废弃次数与花费，且把占用别的请求的队列影响纳入负载评测。

## 逐任务预算和整服务预算为什么都要有

一条父请求可以给自己设最多 3 次工具调用，但同一秒进来 100 个复杂请求，仍可能压满模型并发槽和下游连接池。反过来只做全局限流，一个请求又可能吃掉大部分资源。单请求预算管一次任务可以走多远；并发上限、队列和入口拒绝管所有请求能否共享系统。后台诊断与前台低延迟请求若共享模型配额，还需要隔离资源或设置优先级、死亡线与熔断恢复条件。调大线程池不代表模型服务端增加了计算能力。

放到地图服务里，搜索建议在输入过程中会反复触发，新字符可能使前一次请求变成过期结果。若每个 keystroke 都启动多轮 Agent，即使最后答对也可能在用户已经输入下一字符后才回来。可以让确定性建议继续满足短请求，用户明确点开“为什么没找到/比较两个地点”时才启动具有不同目标时延的 Agent。这里是按用户动作和信息价值作产品设计；具体阈值和负载都必须通过真实使用数据验证。这比把所有 textsearch 或 suggestion 请求统一接到一个大模型循环更符合可解释的工程取舍。

## 两类实验回答两类架构问题

第一类是同预算消融：保持模型版本、公开数据快照、业务工具、输入、输出义务、题型和总资源上限一致，只改变决策方式，问“机制本身对哪些任务有帮助”。第二类是端到端选型：允许各方案合理优化，但必须满足同一外部目标与质量底线，问“哪个服务值得部署”。第一类如果放任一方额外拥有实时资料，就无法归因；第二类若刻意阻止某方案使用其正常缓存，又可能低估其真实表现。实验命名和结论中都要写清这一点。

架构决策应留下可重审的条件。例如真实请求中可安全直出的比例大幅下降，快路径节省的小额时间可能抵不过额外路由成本；如果复杂任务中的子分支频繁共享中间证据，复制多个上下文又可能比一套单 Agent 状态更贵。先写出什么测量会推翻当前选择，后续就能在负载或模型能力变化时理性调整。

## 给架构选型算一笔机会成本

用一个简单的不等式解释何时值得多问一次模型。设当前直接回答会出错的概率为 p，某个追加动作在已有信息下能够纠正错误的条件概率为 q，避免一次错误的价值为 V，追加调用的时间、费用与用户等待成本折算为 C。在这个简化决策里，追加动作的期望收益约为 p×q×V，只有它超过 C 才有理由继续。这里没有要求上线时真用一个精确浮点值；公式帮助团队分清两个常被混起来的判断：当前确实有不确定性，以及这一次额外调用能否带来新证据。

比如用户问实时座位，工具清单里只有常规开放表。此时不确定性 p 很高，但重复读表能补上实时事实的 q 接近零，再加一个“复核 Agent”也不会凭空出现客流数据。换成材料预审，候选结论来自昨日版本，而工具能读今天的新材料，追加读取的 q 可能明显更高。若涉及不可逆业务动作，不能把硬授权约束简化成期望收益；不满足授权时即使收益再高也不可执行。公式只在合法动作之间比较。

对一名熟悉线上 Java 服务的工程师，这自然引出一种分级设计：规则处理便宜且可证实的命题；单 Agent 处理要看观察才能决定的请求；独立 worker 只用于分支内部确实需要探索的任务。记录每次升级策略的触发条件、获得了什么新事实以及代价。若额外推理经常没有改变任何动作或结论，先试验删除该轮，再用困难题和故障题验证是否退化。这比盲目给所有节点升级模型更能解释为什么系统值得部署。

细问“误路由怎么赔偿”时，先看已经产生的效果。只读快路径发现前提不足，可以带着已核实的对象与证据回退；已经发出的草稿通知却不能靠重新走慢路径收回。因此共享授权与业务校验要放在各策略最终都绕不开的位置，快慢两路不能有不同的写权限判断。路由组件可以调交易成本，不能自行改变执行能力。

## 路由器出错时，应该在哪一层放回退

把“按普通表查周末”误分给实时工具，只会带来一次不必要读取；把“查实时余座”误分给普通开放表，却可能输出有害的肯定承诺。两种错误的损失不对称。可以将路由决策拆成“建议路径”和“路径执行前置条件”两步。建议路径只用轻量证据；接收路径核验自己是否真的持有足以作答的字段。快路径若发现用户要的属性不在覆盖范围内，返回结构化原因给一次受限回退，避免在不同策略之间来回弹跳。

路由策略本身也能离线标注。给每题列“最便宜且满足约束的路径”和“禁用路径”，允许多个等价答案。考察路由器在输入缺字段、同义表达、用户换意图、工具暂不可用时会不会把困难题强塞进快路径。生产观测中则要区分路径命中率、错误直出率、回退成功率与回退后的真实端到端代价。若只优化快路径命中率，最简单的做法是让它接受所有请求；没有正确性前提的指标会把架构推向与产品目标相反的方向。

## 面试推演：两秒内解释一条搜索异常，该不该上多 Agent

先澄清两秒是首条可用事实、完整正确报告，还是用户必须在两秒内得到终态。简要的事实如“目标出现在已记录候选中”可以由 Java 解析器先给出；根因解释需要比较多个阶段，且数据缺失时只能报告证据边界。如果必须两秒内给完整根因而输入不含决定性证据，再多 worker 也无法保证正确。可以设计先出有根据的事实、在剩余时限追加分析、到期标示部分完成。然后用同样输入分别跑固定、动态、计划并发，逐题记正确性、截止内完成率和总资源，而不承诺由架构名称推出的时延。[可核算三种策略的 Java 教学模型](../../examples/architecture/ArchitectureLab.java)
